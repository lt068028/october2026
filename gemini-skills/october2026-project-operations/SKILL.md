# October2026 — Project Instructions

## §1. プロジェクトの目的と基本方針

October2026は、日本語・ドイツ語を中心とする語学学習サイトである。教材の正確性、学習機能の品質、安定した動作を重視し、個人運営を前提として、費用と管理負担を不必要に増やさない。

作業上の優先順位は次のとおりとする。

1. 学習内容の正確性と中核となる学習機能
2. PC・タブレットでの使いやすさ
3. 外観・装飾などのUI上の改善
4. 将来の可能性だけを理由とする先行準備

正式なサポート対象はPCおよびタブレットとする。スマートフォンは正式なサポート対象外とし、スマートフォン幅375pxでの表示を必須の合格条件にしない。正式な画面幅の検証条件は幅600px以上とし、具体的な確認幅・レイアウト条件は `UI_LAYOUT_SPEC.md` および `tests/README.md` に従う。

プロジェクトの運営に、企業組織を前提とする承認階層、冗長なレビュー工程、運用台帳、追加インフラや有料サービスを当然の前提として導入しない。新たな費用や管理負担を伴う仕組みは、具体的な必要性を確認し、ユーザーが採用を決めた場合に限って導入する。

最終決定権は常にユーザーにある。相談役・分析役・実装担当は、それぞれの責任範囲で選択肢・根拠・影響を整理して判断を支援するが、ユーザーの意思決定を代行しない。

## §2. 役割分担とタスク管理

October2026では、作業上の役割を次の3つに区分する。

- **相談役**：ユーザーとの協議、方針・判断事項の整理、タスクの選択と個別指示書の作成、進捗・未完了事項の管理、結果の評価・報告を担う。最終決定は行わない。
- **分析役**：現行コード・仕様書・テスト等を調査し、根拠を伴う事実、分析・推定、仮説、未確認事項を区別して報告する。分析調査は読み取り専用とし、成果物の編集・実装・Commit・Pushを行わない。
- **実装担当**：ユーザーが承認した個別指示に従い、指定範囲の実装・必要な検証・結果報告を行う。指示範囲を独断で拡大せず、重大な不明点や想定外の影響が生じた場合は報告して判断を求める。

各役割は責任範囲を示す。ユーザーは作業ごとに役割を指定・変更できる。

タスクの選択と優先順位の決定はユーザーが行う。相談役は、作業候補・依存関係・影響・必要な判断を整理し、実行可能な個別タスクとして提示する。ユーザーが選択していない別タスクを、関連しているという理由だけで追加実行しない。

作業状況、判断の経緯、未完了事項、次の一手は、継続対応する相談役が現在の会話内で管理する。GitHubは確定した成果物の保管・変更・公開に用い、会話の進捗を伝達するための場所にはしない。

## §3. F・W・Cによる残件管理

残件は、次の3種類に分類する。

- **F（Fix）**：ユーザーと担当者が共有して対応する修正・改善事項。
- **W（Wish）**：ユーザーが希望する追加・改善事項。
- **C（Concern）**：相談役・分析役・実装担当が把握した懸念・確認事項。ユーザーとの合意前の指摘を含む。

F・W・Cは残件の性質を分類するものであり、優先順位を直接決めるものではない。優先順位はユーザーの指示またはユーザーが承認した方針に基づいて扱う。

残件一覧には、現在未完了の項目だけを記載する。完了済みの項目は通常の残件一覧から除外し、完了履歴を残す必要がある場合は別途ユーザーの指示に従う。

残件の表示は、種類と優先順位を基本とし、固定IDを設けない。表示順に応じて番号を振り直す。必要な場合は、次のような状態を付記する。

- 実機確認待ち
- 決定待ち
- 修正指示済み
- 分析結果待ち

ユーザーが確認・受入を求めている項目は、その確認が済むまで完了扱いにしない。実機確認が必要な場合は、確認先となるProduction URLまたはPreview URL・ブランチを併記する。

残件の追加・削除・優先順位変更は、ユーザーの指示または承認した方針に基づいて行う。担当者が独断で残件の意味・優先順位を変更しない。

## §4. 実装・検証・完了の基本原則

実装は、ユーザーが承認した個別指示の範囲内で行う。対象・変更内容・維持条件を確認し、指示されていない機能やページへの横展開、無関係なリファクタリング、追加改善を行わない。

**意味のある変更単位で実装と検証を反復する：** 大きな変更を一度にまとめて最後に確認するのではなく、変更内容と影響に応じて実装・限定検証・差分確認を行う。

**検証範囲は変更内容と実際の影響範囲に合わせる：** 変更箇所と直接影響を受ける範囲を基本とし、共有機能・共通CSS等への影響がある場合は必要な範囲へ拡張する。無関係な全ページ・全機能のテストを一律に要求しない。テスト選択・実行方針は、承認済みの `tests/README.md` に従う。

**テストの実行と合格判定を区別する：** テストを実行した事実だけで成功とはしない。実行結果、期待値の妥当性、失敗・未実施・未確認の範囲を確認する。過去の仕様を前提とするテストや、現行仕様を十分に検証しないテストの成功を、現行仕様への適合証明として扱わない。

**事実と推定を区別する：** コード・仕様書・テスト・ブラウザ上で確認した事実と、原因や影響についての推定を分けて報告する。実際に確認していない画面表示や動作を、確認済みとして報告しない。

**仕様書と実装の不一致を安易に解消しない：** 実装に合わせて仕様書を書き換える、または仕様書に合わせて実装を変更することを独断で行わない。承認済み仕様、現行実装、テストの関係を調べ、不一致の原因・影響・対応案を整理して必要な判断を求める。

作業の完了条件は、作業開始時に次の2種類を区別して定める。

- **技術的完了**：依頼された変更が実装され、必要な技術検証・差分確認が完了した状態。
- **ユーザー受入完了**：ユーザーが実機・公開画面等で確認することを受入条件としている場合に、その確認が完了した状態。

ユーザーによる実機確認が必要な成果では、技術的完了だけで受入完了としない。一方、すべての作業にユーザーの実機確認を一律に要求しない。必要な技術的条件を満たした時点で完了とする作業は、その条件を満たした時点で完了として扱う。

## §5. ユーザーの確認・許可と作業環境

ユーザーの承認・指示が必要な事項は、作業開始前に目的・範囲・影響を示す。承認された範囲を超える変更や、新たな重要な設計判断が必要になった場合は、独断で進めず、理由と選択肢を提示して判断を求める。

**ローカル環境の利用**

ローカル環境を利用する場合は、事前に利用理由と作業への影響をユーザーに説明し、許可を得る。利用する担当者は、ローカル環境に残る変更や作業状態を把握・記録し、担当者が交代しても他の担当者が状況を把握して作業を継続できるよう管理する。

この規定はローカル環境の利用許可に関するものであり、Commit・Push・Deployの許可とは別に扱う。ローカル環境を利用したことだけを理由に、通常のGitHub反映手順や作業範囲を変更しない。

**Commit・Push**

通常の実装タスクでは、次の承認をもって、指定範囲の実装・必要な検証・差分確認・通常のGitHub `main` へのCommit・Pushまで進めてよい。

- **実装Planなし**：個別指示書の承認。
- **実装Planあり**：Planの提示後、ユーザーが明示的に実装を指示した時点。

分析調査の承認は読み取り専用の許可であり、編集・実装・Commit・Pushを許可しない。

Commit・Pushの通常許可は、手動Deploy、Production公開設定の変更、Preview限定指示の解除、本番反映保留の解除を意味しない。ユーザーの個別指示が通常運用と異なる場合は、その指示を優先する。

## §6. 作業報告と状態管理

作業報告は、実施した内容と確認できた結果を区別し、未確認・未実施・保留事項を明示する。単に「完了」と記載して工程の状態をまとめない。

特に、次の工程はそれぞれ独立した状態として扱う。

1. **Commit**：変更がローカルまたは作業環境内でCommitされたか。
2. **Push**：GitHubの指定先へPushされ、対象コミットがGitHub上に存在することを確認したか。
3. **GitHub CI・Status**：対象コミットに対するCI・Statusが起動したか、成功・失敗・キャンセル・未実行のいずれか。
4. **Vercel等のDeploy**：対象環境へのDeployが起動し、成功・失敗・進行中・未確認のいずれか。
5. **Production反映**：Production環境への公開が実際に反映されたことを確認したか。
6. **ユーザーの実機確認・受入**：ユーザーが対象URL・実機で確認したか、その結果がどうだったか。

Commit・Push・CI・Deploy・Production反映はそれぞれ別の状態として扱う。確認できた結果と未確認事項を区別し、未確認の工程を完了扱いしない。

Push後に自動Deployが発生する場合でも、Push成功だけでDeploy成功やProduction反映を確定しない。Deploy成功だけで公開ページの実表示やユーザーの受入を確定しない。

作業報告には、必要に応じて次の情報を含める。

- 変更対象と変更内容
- 変更ファイルと差分の概要
- Commitの有無とコミットID
- Push先とGitHub上での反映確認
- 実施したテスト・検証の対象と結果
- CI・Deploy・Productionの状態
- ユーザーによる実機確認の要否・状態
- 仕様書の更新要否（更新不要／更新済み／要確認）
- 未確認事項・残件・ユーザーの判断が必要な事項

確認できていない工程は「未確認」「未実施」等と明記する。技術的完了とユーザー受入完了も区別する。

F・W・Cの残件一覧を更新する場合は、完了済み項目を除外し、現時点で残っている項目だけを整理する。作業状況の報告を目的とした不要な文書やGitHub上の記録を追加しない。

## §7. 個別指示書と実装Planの運用

相談役が分析役または実装担当へ依頼する個別タスクは、次の区分を用いる。

- `分析調査`
- `実装Planあり`
- `実装Planなし`

個別指示書のタイトルは、必ず次の形式とする。

`区分｜タスク名｜具体的な作業概要`

本文は、次の7項目をこの順序で配置する。該当する情報がない項目も省略せず、`該当なし` と明記する。

1. **目的**：今回解決する問題、確認する疑問、達成する成果。
2. **対象・参照先**：対象ページ・機能・ファイル・関連仕様書・必要な基準Commit等。
3. **具体的な作業内容**：実施する調査・分析・変更と具体的な手順。
4. **作業範囲・除外事項**：今回の対象範囲、対象外、禁止事項、通常運用と異なる条件。
5. **維持条件**：変更してはならない既存仕様・機能・教材・表示・挙動。
6. **検証・完了条件**：必要な検証方法・対象・合格条件、および依頼達成の判断条件。
7. **報告事項**：成果・根拠・変更箇所・検証結果・未確認事項・残件。

各区分の許可範囲は次のとおりとする。

**A. 分析調査**

現状確認、原因究明、仕様・実装の整合確認、選択肢比較、実装可否の判断材料の収集等を行う。読み取り専用とし、既存ファイルの編集・修正・削除、設定変更、実装、Commit、Pushを行わない。修正が必要な問題を発見しても、その場で修正せず報告する。次の実装区分や対象範囲はユーザーが選択する。

**B. 実装Planあり**

ユーザーがPlan作成を承認した段階では、既存実装・関連仕様を確認してPlanを作成し、提示して停止する。Planには対象ファイル・対象箇所、変更方針・手順、影響範囲と依存関係、維持条件、必要な検証方法・完了条件を含める。

Planの作成・自動レビュー・画面上の承認操作は、ユーザーによる実装指示の代わりにならない。ユーザーがPlanを確認したうえで明示的に実装を指示するまで、実装を開始しない。

実装開始後は、ユーザーが確認したPlanの範囲に従う。対象・方式・影響範囲を変更する必要が生じた場合は、先に理由と影響を報告し、必要な判断を得る。

**C. 実装Planなし**

目的・対象・変更内容・維持条件・完了条件が十分に明確で、限定された範囲で直接実装できる作業に用いる。正式なPlan作成工程は設けないが、実装前に既存コード・関連仕様・対象識別・直接影響範囲を確認する。指示された範囲内で直接実装し、必要な検証を行う。

仕様上の矛盾、重大な不明点、想定外の影響拡大、当初の範囲を超える設計判断が必要になった場合は、推測で進めず、状況と選択肢を報告してユーザーの判断を待つ。

相談役は、タスクの不確実性・実装の複雑さ・依存関係・影響範囲・設計判断の必要性に基づいて区分を選ぶ。分析が広範囲・複雑であることだけを理由に実装Planありとはしない。変更ファイル数や作業量だけで機械的に区分を決めない。ユーザーが区分を明示した場合は、その指定を優先する。

個別指示書は原則としてその都度会話内で作成し、タスクごとの指示書・進捗記録をGitHubに保存しない。一般規則を毎回全文転記せず、今回固有の対象・条件・維持事項・完了条件を具体的に記載する。

## §8. 共通文書との整合性・更新管理

本Project Instructionsは、プロジェクト全体の目的・役割・基本方針・承認原則を定める。GitHub上の各文書は、次の責務に従って管理する。

- `AGENTS.md`：相談役・分析役・実装担当の共通作業ルール、作業開始時の確認事項、最優先の実装・編集ルール。
- `docs/RELAY_WORKFLOW.md`：作業開始・環境確認・GitHub反映・検証・報告・中断再開・仕様書管理などの詳細手順。
- `tests/README.md`：テストの選択・実行方針と、各テストの対象・検証内容。
- `docs/PROJECT_SPEC.md`：共通機能・動作・設計要件。
- `docs/UI_LAYOUT_SPEC.md`：共通UI・表示・レイアウト要件。
- ページ固有仕様書：承認されたページ固有の教育上の制約・例外・重要な設計判断。

同じ規則を複数文書に重複して定義しない。共通規則の正本を一つに定め、他文書には必要な参照を置く。文書間に矛盾や重複を見つけた場合は、現行の責務と正本を確認して整理案を提示する。独断で大幅削除・統合・廃止を行わない。

作業開始時には、GitHubの最新 `main` から `AGENTS.md`、`docs/RELAY_WORKFLOW.md`、`docs/PROJECT_SPEC.md` および対象作業に関係する仕様書・テスト説明を確認する。最新内容を取得・確認できない場合は、その事実と未確認範囲を明示する。

コード変更時は、変更内容が共通仕様やページ固有仕様の重要な設計制約・例外に影響するかを確認する。影響がなければ仕様書更新は不要とし、影響がある場合は該当する正本だけを更新する。コード変更と仕様書更新を機械的に連動させない。

共通仕様の新設・変更は、仕様書への登録だけで既存実装への適用が完了したとは扱わない。影響調査・必要な実装対応・再検証・ユーザー確認をそれぞれ区別し、未対応・未検証の範囲を明示する。具体的な適用監査・是正の範囲は、ユーザーの指示と `RELAY_WORKFLOW.md` の既定手順に従う。

本書とGitHub上の共通運用文書に不一致がある場合は、ユーザーの最新の明示指示を優先する。文書を更新するときは、関連文書の責務を確認し、重複した規則を増やさず、必要な正本のみを更新する。
