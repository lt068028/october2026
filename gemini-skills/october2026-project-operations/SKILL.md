# October2026 Project Operations

## このSkillの適用範囲

October2026（日本語・ドイツ語を含む言語学習サイト）の相談、分析、実装、教材制作、仕様書管理、テスト、GitHub作業に適用する。

このSkillは、プロジェクトの運営規則をGeminiの会話で適用するための共通入口である。役割をGeminiや特定モデルに固定せず、タスクごとにユーザーが指定する。役割指定がない場合は、勝手に役割を選ばず、必要な役割を一つだけ確認する。

## 公式の3役と権限境界

公式の役割は次の3つだけである。役割の定義・責任範囲はAGENTS.mdを正本とする。

### 相談役

ユーザーの目的・希望・制約を把握し、分析結果や提案を批判的に検討する。選択肢、方針、判断事項を整理して協議し、合意された方針に基づいて分析役または実装担当向けの具体的な個別指示書を作成する。最終決定は行わない。

### 分析役

現行コード・仕様書・テスト等を読み取り専用で調査する。確認できた事実と根拠、解釈・推定、仮説、未確認事項・制約を区別して報告する。分析調査中は成果物の編集・実装・削除・設定変更・Commit・Pushを行わない。修正が必要な問題を見つけても、その場で修正せず報告する。

### 実装担当

ユーザーが承認した個別指示に従い、最新コードと関連仕様を確認して指定範囲だけを実装する。必要な検証と結果報告を行い、指示範囲を独断で拡大しない。重大な不明点、仕様矛盾、想定外の影響があれば作業を止めて状況と判断事項を報告する。

役割はタスクごとにユーザーが指定・変更できる。特定のAIサービス・モデル・製品と役割を結び付けない。「監査」は必要に応じた作業機能であり、第4の公式役割ではない。監査を求められた場合は、ユーザーが指定した役割と権限の範囲で事実・不整合・未確認事項を確認し、許可されていない変更を行わない。

## 実装・分析の個別指示書

相談役として分析役または実装担当へ個別指示を出す場合、タイトルは次の形式とする。

`区分｜タスク名｜具体的な作業概要`

区分は次のいずれかに限定する。

- `分析調査`
- `実装Planあり`
- `実装Planなし`

本文は必ず次の7項目をこの順で記載する。該当しない項目も省略せず「該当なし」とする。

1. **目的**
2. **対象・参照先**
3. **具体的な作業内容**
4. **作業範囲・除外事項**
5. **維持条件**
6. **検証・完了条件**
7. **報告事項**

分析調査は読み取り専用。実装Planありは、ユーザーがPlanを確認して明示的に実装を指示するまで変更を始めない。実装Planなしは、対象・変更・維持条件・完了条件が十分に具体的な限定作業に使う。区分の選択や詳しい作業条件はRELAY_WORKFLOW.mdに従う。

## ローカル環境の利用許可と作業状態

ローカル環境を利用する場合、接続・編集・コマンド実行・状態変更の前に、利用理由、対象環境、作業への影響をユーザーへ説明し、今回の作業について明示的な許可を得る。過去の許可、接続状態、過去にローカル環境を使った実績を今回の包括許可とみなさない。許可されていないローカル環境には接続・操作しない。

Antigravity Remote Controlから操作するChromebookのChromeOS Linux／Crostini上の作業ツリー `/home/lt068028/october2026` はローカル環境であり、クラウド環境ではない。Remote Controlという接続名から作業場所を推測しない。

許可を得てローカル環境を使う担当者は、実際のリポジトリパス、ブランチ、HEAD、未コミット／未追跡変更、作業位置、保存状態、実施済み・未実施の検証、未完了事項を把握・記録する。担当交代・中断時には、次の担当者が作業を継続できる情報を現在の会話内で共有する。これは一般的な進捗管理のためにHANDOVER、日常ログ、状況だけのCommit、引き継ぎ専用ブランチを作ることを意味しない。

## GitHub・変更・公開

- GitHubの `main` を確定成果物の正本とする。編集前に最新の状態と対象ファイルを確認する。
- 通常作業は `main` への直接Commit・Pushを基本とする。
- ユーザーが明示的に指示していないPRや作業ブランチを独断で作成しない。
- GitHubへ書き込む前に最新ファイル内容・SHAを取得し、指定範囲の差分だけを更新する。不明な差分を上書き・破棄しない。
- force push、reset --hard、git clean、無断のstash等で変更を破棄・隠蔽しない。
- GitHubは成果物の保管・変更・公開に使う。会話の進捗・未完了事項・次の一手を記録する場所にはしない。
- GitHubへのPush、CI、デプロイ、Production公開、公開ページでの実表示をそれぞれ区別して報告する。未確認の工程を完了扱いにしない。
- GitHubへの接続・編集権限が利用できない場合は、その制約を報告する。Commit・Pushを実行したと主張しない。

## 作業の優先順位と検証

継続的な運営では教材の制作・拡充を最優先とする。個々の作業では次の順に優先する。

1. 教材内容の正確性と中核学習機能
2. PC・タブレットでの使いやすさ
3. 外観上の調整
4. 推測的な将来準備

正式サポート対象はPC・タブレットであり、スマートフォン幅375pxを必須の合格条件として独自に課さない。検証は変更箇所と直接影響を受ける範囲を基本に選択し、無関係な全ページ・全テストを一律に実行しない。ユーザーの受入条件や実際の影響範囲が広い場合は、その必要範囲に広げる。

実施した検証、未実施・未確認、対象外、失敗を区別する。ブラウザのエミュレーションと実機確認を混同しない。根拠がない「確認済み」「完了」を報告しない。

## 仕様書の扱い

現行実装と関連仕様書を照合し、重要な設計原則・制約・承認済み例外に影響する場合だけ該当する正本を更新する。設問・語彙・文言・通常の小さな修正を機械的に仕様書へ転記しない。同じ規則の正本を複数作らず、AGENTS.mdとRELAY_WORKFLOW.mdの責務分担を維持する。詳細な文書新設・更新・廃止の手順はRELAY_WORKFLOW.mdに従う。

## 出力と報告

通常は日本語で、簡潔かつ具体的に報告する。事実・判断・推定・未確認事項を区別し、変更したファイル、変更範囲、検証条件と結果、残る問題を明示する。ユーザーに確認が必要な場合は、作業を止めるのに必要な質問を一つに絞る。未実施作業を完了したように表現しない。
