# ドイツ語ドリル開発・参照ガイド（German Development Guide）

**版：2026-11-08策定**  
**対象：Deutsche Übung シリーズ（`uebung*.html`, `uebung*.js`, `tests/uebung*.cjs`）**

---

## 1. 目的と開発方針

本書は、今後 Deutsche Übung 1.2 以降のドイツ語ドリルを新規作成・改修する際、**日本語ドリル（`practice*.js` 等）の実装ファイルを毎回横断的に調査する必要を排除し、開発効率を最大化するための作業標準ガイド**です。

現在の **`Deutsche Übung 1.1`（`uebung1.1.html` / `uebung1.1.js`）をドイツ語ドリルの第一参照実装**とし、仕様・構造・制御はこの実装と [ドイツ語ドリル専用仕様書](GERMAN_DRILL_SPEC.md) に基づいて行います。

---

## 2. 参照順序と仕様の優先関係

ドイツ語ドリルの作業では、次の順序で必要な情報を確認する。これは調査の進め方であり、仕様の優先順位を示すものではない。

1. **作業指示とプロジェクト共通の作業ガード**：`AGENTS.md`および[RELAY_WORKFLOW.md](RELAY_WORKFLOW.md)の該当手順を確認する。
2. **ドイツ語専用仕様**：[GERMAN_DRILL_SPEC.md](GERMAN_DRILL_SPEC.md)と本書の該当規則を確認する。
3. **対象ページの現行実装**：対象の`uebung*.html`／`uebung*.js`を確認し、DOM、データ、依存関係、現状を把握する。
4. **対象の専用テスト**：`tests/uebung*.cjs`を確認し、関連する契約と期待値を把握する。
5. **必要な共通仕様・共通資産**：`UI_LAYOUT_SPEC.md`、`PROJECT_SPEC.md`、および対象ページが直接利用する共通モジュールを、影響範囲に応じて確認する。

**仕様の正否を判断する際は、承認済みの仕様・作業指示を現行コードの状態より優先する。** コードは現状を把握するための証拠であり、仕様に反する実装が存在しても、それだけで仕様を変更・上書きしたものと扱わない。仕様間の矛盾、承認状態の不明、意図が判断できない差異があれば、独断で決着させず作成者に確認する。

## 3. 日本語ドリルファイルの参照禁止と例外規定

### 3.1 原則禁止
通常のドイツ語ドリルの新規作成、修正、リファクタリング、不具合調査では、**日本語ドリル（`practice*.js`, `practice*.html`, `composition*.js`, `pronunciation*.js` 等）を横断検索・参照してはならない**。

### 3.2 例外条件（日本語ファイルの参照が許可される4ケース）
以下に該当する場合に限り、例外として日本語ドリルファイルを参照することができます。
1. **共通モジュール仕様の判断困難**: 共通モジュール（`drill-audio-session.js` 等）の細部仕様や利用制約が、ドイツ語側の資料やコードだけでは確定できない場合。
2. **日本語固有機能の新規移植**: 日本語側にしか存在しない新しい機能（例: 新たなUIコンポーネントや録音分析等）をドイツ語ドリルへ初めて移植・導入する場合。
3. **共通機能変更時の影響調査**: `drill-audio-session.js` や `style.css` の共通セレクタを変更する際、日本語側への波及を調査する必要がある場合。
4. **既存テスト失敗の原因分析**: 変更によって日本語ドリルの既存自動テスト（`tests/*.cjs`）が失敗し、日本語側の文脈分析が必要となった場合。

### 3.3 作業報告への明記義務
例外的に日本語ファイルを参照した場合は、作業報告において **「参照した日本語ファイル」および「参照が必要となった例外理由」を簡潔に明記** すること。

## 4. 共通モジュール変更時の影響確認と回帰テスト

`drill-audio-session.js`、`style.css`、`tooltip-layout.js`などの共通資産を変更する場合：

1. **フォーク（複製）の禁止**：
   - 共通モジュールをドイツ語専用に複製せず、既存の共通資産を共有する。
2. **影響範囲の特定**：
   - 変更する関数・セレクタ・APIの利用箇所を確認し、影響を受けるページ、機能、テストを特定する。
   - 日本語側を含む他ページへの影響が想定される場合は、その範囲を調査する。ただし、関係のない全ページのソースを無条件に読み込まない。
3. **変更に対応する検証**：
   - 変更箇所と実際の影響範囲に対応する専用テスト・共通テストを選び、必要なものを実行する。
   - テスト全体の実行は、変更の影響範囲や作業指示上必要な場合に行う。全テスト実行を一律の前提にしない。
   - 未実施の検証範囲、既知の失敗、未確認事項を完了報告で区別する。
4. **変更の局所化**：
   - ドイツ語固有のスタイルは原則として`style.css`内の`.uebungXX-page`スコープに閉じ込め、共通セレクタの上書きを最小限に留める。共通仕様を変更する場合は、影響範囲と適用対象を別途確認する。

## 5. 調査効率化の具体的ルール

必要な根拠を確保しつつ、無関係な探索や重複作業を避ける。

- **直接依存の特定**：作業開始時に、対象ページと直接依存するファイル（HTML、JS、専用テスト）を特定する。
- **必要範囲の読み取り**：ファイル全体を無差別に読み込まず、関係する関数・見出し・行範囲を中心に確認する。読み取り方法やツールを特定のコマンドに固定しない。
- **重複読み込みの抑制**：同一会話内で確認済みのファイル・範囲は、内容が更新された、追加範囲が必要になった、または再確認が必要な根拠がある場合を除き、繰り返し読み込まない。
- **「参考になりそう」による探索の禁止**：日本語ページを曖昧な動機で探索しない。§3の例外条件に該当する場合のみ参照する。
- **段階的な調査範囲の拡大**：対象コードと専用仕様・テストから調査を始め、原因や影響範囲を確定するために必要な場合に限り、共通モジュール・共通仕様・他ページへ範囲を広げる。
- **検証と作業確定**：検証内容、変更の保存・反映方法、Commit／Push／PR等の扱いは、作業時点の`AGENTS.md`および[RELAY_WORKFLOW.md](RELAY_WORKFLOW.md)に従う。本書でローカルコマンドや特定のGit操作を一律に必須化しない。効率化を理由に、指示された検証や必要な安全確認を省略してはならない。

## 6. 新規ドイツ語ドリル（Deutsche Übung 1.2+）作成の標準手順

1. **作成対象と学習設計の確定**：
   - 新しいドリルの学習目標、対象文型、設問構成、地域変種の扱いを定め、既存の承認済み教材・仕様との整合を確認する。
2. **第一参照実装の利用**：
   - `uebung1.1.html`／`uebung1.1.js`をドイツ語ドリルの第一参照実装として利用する。複製・再利用する範囲は新規ページの構造と既存共通機能に合わせて判断し、タイトル、見出し、スクリプト参照、ページ固有識別子等を適切に更新する。
3. **カリキュラムデータ（`drillsData`）の作成**：
   - `drillsData`内のタイトル、指示文、`example`、`items`を新しい学習目標に合わせて作成する。
   - 必要に応じて`highlightGrammar()`の対象語を調整する。
   - 地域変種がある項目は、承認済みのドイツ語仕様に従って`regionalModels`および`allowedAnswers`等を定義する。
4. **専用テストとナビゲーション**：
   - 既存の`tests/uebung*.cjs`から対象機能に適したテスト構成を参照し、新ページの契約に対応する専用テストを作成・更新する。
   - `index.html`等のナビゲーション登録が必要な場合は追加する。
5. **検証とGitHubへの反映**：
   - 対象変更と影響範囲に応じた検証を行い、実行結果と未確認事項を区別する。
   - 変更の保存・反映・公開方法は、作業時点の`AGENTS.md`および[RELAY_WORKFLOW.md](RELAY_WORKFLOW.md)に従う。特定のブランチ、ローカルコマンド、Commit／Push手順を本書で一律に指定しない。
