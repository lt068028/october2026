# October2026 — AI作業・GitHub運用手順

> **版：2026-11-15.1**
>
> **運用の前提**：GitHubは成果物の保管・変更・公開に使う。相談エージェントへの作業状況の伝達には使わない。

## 原則
- GitHubの `main` を、確定したコード・仕様書・テスト等の成果物の基準とする。GitHubは成果物の変更履歴と公開のために使い、会話の進捗・未完了事項・次の一手を保管する場所にはしない。
- 作業状況・判断の経緯・未完了事項は、継続対応する相談エージェントが現在の会話内で管理する。`HANDOVER.md`、日常作業ログ、状況だけを記録するCommit、引き継ぎ専用ブランチを新設・更新しない。
- **クラウド優先・PCローカル編集禁止**：コード・文書編集はCodex Cloud、Antigravity Remote Agents、権限のあるGitHub API等、PCのローカル作業ツリーを書き換えない方式で行う。PCローカル編集へ自動的に切り替えない。クラウド機能・GitHub権限が利用できなければ編集前に支障を報告し、明示許可なしにPCローカル編集で代替しない。
- クラウド内の作業ツリーを使用する場合は、対象リポジトリ・ブランチ・基準コミット・既存変更を確認する。不明な変更を上書き・破棄しない。GitHub APIで直接編集する場合も、更新対象ファイルの最新内容・SHAを取得してから更新する。
- 複数の相談エージェントやサービスを順番に交代させる運用を前提にしない。担当交代・会話切断への備えだけを理由にPushやブランチ作成を行わない。
- force push（--force-with-leaseを含む）、reset --hard、git clean等の無断破棄は禁止。履歴分岐を無断でmerge/rebase/resetにより解消しない。stashで不明な変更を自動的に隠さない。

## GitHub作業・PR運用方針（2026-11-14改定）

**基本原則：mainへの直接Pushを原則とし、PRは必要な場合だけ使用する。**

### 通常運用
1. 通常の作業は、原則として `main` への直接Commit・Pushで完了させる。
2. ユーザーが実装・修正とGitHubへの反映を指示した場合、指定された変更範囲の検証・差分確認を終えた後、別途PR作成やPush承認を求めず、原則として `main` へ直接反映する。
3. 作業テーマごとにPRを作成することは必須ではない。
4. 同一テーマの作業を不必要にブランチ・PRへ分割しない。
5. Commit・Push前には変更範囲、差分、検証結果を確認し、指定外の変更を混入させない。

### PRを使用する場合
PRは次のような場合に限定して利用できる。
- 変更内容の事前レビューが特に有効な場合
- 並行作業や複数担当者間の統合が必要な場合
- Preview環境で独立した確認が必要な場合
- 変更のリスクや規模から、main反映前の分離が合理的な場合
- ユーザーがPRの利用を指定した場合

PRは任意の手段であり、通常作業に必須の工程ではない。
PRを利用する場合も、当初のユーザー指示にmainへの反映まで含まれていれば、検証完了後に別途の承認を取り直す必要はない。指示がレビュー・PR作成までに限定されている場合は、その範囲で停止する。

### Production反映との関係
- `main` へのPushによってVercel等のProduction自動デプロイが発生する設定の場合、その動作を事前に把握しておく。
- ユーザーからGitHubのmainへの反映を指示された通常作業では、そのPushに伴う自動デプロイを想定される結果として扱う。別途PRを必須にしたり、同じ指示について二重の承認を求めたりしない。
- ユーザーが明示的にPreview限定・本番反映保留等を指定した場合は、その指定を優先する。
- 本番反映の仕組みが不明な場合は、確認できた範囲と不明点を報告し、事実を推測で補わない。

この方針は日本語・ドイツ語の開発双方に適用する。言語別に必ずPRを分離するという意味ではない。既存の未完了PRを無断で閉じず、統合先と保存済み変更を確認してから整理する。

## 1. 作業開始時の確認

1. 対象リポジトリが `lt068028/october2026` であることを確認し、作業開始前にGitHubの最新 `main` と対象ファイルの状態を取得する。取得できない場合は、最新状態を確認できていないことを明示する。
2. クラウド作業ツリーを使う場合は、現在のブランチ・HEAD・変更済み／未追跡ファイルを確認する。既存変更があれば保全し、出所不明の変更を同期・編集・破棄しない。GitHub APIで直接編集する場合は、更新前に対象ファイルの現行内容とblob SHAを取得する。
3. 最新の `AGENTS.md`、本書、`docs/PROJECT_SPEC.md`、および今回の作業に関係する仕様書・テスト説明を読む。無関係な文書や全ページの実装を機械的に読み込まない。
4. 作業対象・変更範囲・必要な検証を定める。対象や既存変更の状態が不明な場合は推測で編集せず、確認できた事実と支障を報告する。
5. `main` へ反映する直前に最新状態を再確認する。他の変更が先に入っていれば差分を照合し、既存成果を上書きしない。

開始時に毎回定型の環境情報・進捗報告を要求しない。複雑な作業では、対象・基準コミット・作業範囲・検証方針を必要な範囲でユーザーに示す。

## 2. 作業・保存・検証

- 作業単位ごとに差分と関係仕様への影響を確認し、必要な成果物だけを更新する。作業状況を残すためだけの文書変更・Commit・Pushは行わない。
- コード・仕様書等の確定成果をGitHubへ反映する場合は、変更範囲・差分・検証結果を確認し、通常は `main` へ直接Commit・Pushする。PRは事前レビュー、Preview確認、リスク分離、ユーザー指定等、本当に必要な場合だけ使用する。途中状態の引き継ぎだけを目的とするブランチは作成しない。

### ページ作業完了とページ全体テスト（2026-11-04確定／2026-11-14整理）

#### 1. 用語と宣言者
- **ページ作業完了**：作成者が必要な教材内容・練習問題・機能・UI・レイアウト等の制作を終えたと判断した状態。テスト合格や不具合がないことを意味しない。
- **ページ全体テスト**：作成者による「ページ作業完了」の宣言を受けて、当該ページ全体を包括的に検証すること。
- **検証完了**：そのページに必要な検証項目が終了し、必須項目の合格が確認された状態。未実施・未確認・不合格は区別して報告する。
- 宣言するのは作成者であり、AIが独自にページ作業完了を宣言したり、全体テストを開始したりしない。
- 作成者が「ページ作業完了」と宣言したら、対象ページの全体テストへ直ちに移行する。

#### 2. 開始条件とテスト範囲
- 制作中は、変更箇所と直接影響を受ける範囲の限定検証を行う。
- 制作中に対象ページ全体の包括テストを繰り返さない。
- ページ作業完了後は、その対象ページの全体テストを実施する。
- 対象ページの全体テストは、他ページや全リポジトリの全テストを自動的に実行する指示ではない。
- ページ固有テストと共通機能・共通CSSの影響範囲を考慮し、必要な検証を選択する。
- 不具合修正後は、修正箇所と実際の影響範囲を再検証する。
- 全11ページ横断のE2Eテストは、全ページへの影響が想定される場合や全体の総合確認が必要な場合に選択する。1ページの作業完了だけを理由に必須とはしない。
- テストの選択・実行方針は、2026-11-14にユーザー承認された [tests/README.md](../tests/README.md) と整合させる。

#### 3. ページ全体テストの確認範囲
各確認項目の合否は、次の正本に照らして判断する。
- 共通機能・動作要件：`PROJECT_SPEC.md`
- 共通UI・表示・レイアウト：`UI_LAYOUT_SPEC.md`
- ページ固有の教育上の制約・例外：承認済みの該当ページ固有仕様書
- 現在の設問・教材・語彙・表示文言：ページの実装コード
- 自動テストの選択・実行方法：ユーザー承認済みの `tests/README.md`

1. **教材・コンテンツ**
   - Example／Drillの内容
   - 文法・語彙・表記・モデル文・キューの整合性
   - 該当するページ固有仕様との一致
2. **ホバー**
   - 語句と英語訳・ローマ字の対応
   - 表示位置と画面外へのはみ出し
   - 隣接語句・選択欄・録音ボタン等との重なり
   - 折り返しや画面幅変更時の位置ずれ
   - Hover／Display／OFF等、ページで使用する表示モード
3. **レイアウト**
   - 正式サポート対象であるPC・タブレットの表示
   - 文字の折り返し、余白、整列
   - ボタン・プルダウンの配置
   - Light／Darkの表示
   - 検証条件・画面幅は [UI_LAYOUT_SPEC.md](UI_LAYOUT_SPEC.md) の共通レイアウト仕様に従う。
   - ※ スマートフォン幅375pxは必須の合格条件としない。新しい幅の必須条件を独自に追加しない。
4. **機能**
   - 選択肢・プルダウン
   - 録音・停止・再生
   - Autostop／Manual、Autoplay／Manual
   - TTS／STT
   - 回答判定・録音結果保持
   - ページ固有機能
5. **技術**
   - 関連する自動テスト
   - JavaScript構文・実行時エラー
   - 主要な状態遷移
   - ※ すべてのテストを一律実行するのではなく、現在のテスト選択方針に基づいて必要なものを選ぶ。

#### 4. タッチ操作
- タッチ操作の基本動作は共通UIとして検証する。
- 共通実装に変更がなければ、ページごとに同一の基本タッチテストを繰り返さない。
- 共通タッチ実装の変更時は、その共通機能の影響範囲を確認する。
- ページ固有要素やタッチ操作に影響する変更がある場合は、その範囲を追加確認する。
- PC・タブレットを正式サポート対象とする。スマートフォン幅の必須検証へ拡張しない。

#### 5. 結果報告
各確認項目を次の状態で報告する。
- 合格
- 不合格
- 未実施・未確認
- 対象外

ブラウザのエミュレーションと実機確認は区別する。未確認を合格扱いしない。
不具合については、原因、影響範囲、修正内容、再検証結果を報告する。
なお、本規定自体の登録や更新を、ページ作業完了・検証完了と扱わない。

## 3. 作業終了・変更確定

1. 新規作業を止め、進行中の処理を確認する。バックグラウンドの編集・Pushが残らないよう安全に停止し、停止不能ならその状態を報告する。
2. 差分・秘密情報・不要ファイルを確認する。未検証箇所や未完了事項を完了扱いしない。
3. 関係仕様書の更新要否を本書「5. 仕様書管理と継続的整合性確認」で判断し、必要な正本だけを更新する。
4. ユーザーの指示範囲に含まれる確定成果は、検証・差分確認後に `main` へ反映する。PRを使うのは、事前レビュー・Preview確認・リスク分離・ユーザー指定等の理由がある場合に限る。ブランチはそのPR／Preview作業に必要な範囲で使用し、会話中断や担当交代のための途中保存ブランチを常設しない。
5. Push後は送信先とコミットIDを照合する。Production自動デプロイが関係する場合は、GitHubへの反映・CI・デプロイ・公開ページの実表示をそれぞれ区別する。
6. 作業報告では、実装・自動検証・ユーザー実機確認・CI・公開反映を分け、未実施・未確認・未完了を明示する。日常的な進行記録をGitHubへ追加しない。

## 4. 作業中断・再開

- 会話や処理が中断した場合、Commit・Push・検証が完了したと推測しない。現在の会話と実際に利用できる作業環境の状態を確認し、GitHub上の最新 `main` および該当するPR／Previewがある場合はその状態と照合する。
- 作業ツリーに未保存変更が残っている場合は保全し、差分と保存状態を確認する。出所不明の変更を上書き・破棄しない。PCローカル編集を復旧手段として自動的に利用しない。
- 会話の状況伝達や担当交代だけを目的に、HANDOVER、作業ログ、relayブランチを作成しない。再開時は、ユーザーの最新指示・現在の会話・GitHubに実在する成果物と変更履歴を基準にする。

## 5. 仕様書管理と継続的整合性確認

本節をOctober2026の文書管理手順の唯一の正本とし、継続対応する相談エージェントが作業時に適用する。実装内容の転記ではなく、将来も守る設計原則・制約・例外を管理する。

### 5.1 文書の種類・責務・正本

| 情報 | 正本と責務 |
| --- | --- |
| 現在の設問・教材・語彙・表示文言・選択肢 | ページの実装コード |
| 共通機能・動作・設計 | [PROJECT_SPEC.md](PROJECT_SPEC.md)：音声・録音・STT/TTS・状態保持・表記／教材の基本原則・ページ全体テスト基準 |
| 共通表示・操作配置・レイアウト | [UI_LAYOUT_SPEC.md](UI_LAYOUT_SPEC.md)：PROJECT_SPECの機能要件を前提とする共通UI契約 |
| ページ／密接なページ群の重要な制約 | 承認済みの該当ページ固有仕様書。教育上の理由・重要な例外・複雑な固有設計・不変条件を扱う |
| AIの作業手順・同期・文書管理 | [AGENTS.md](../AGENTS.md)は入口・必須ガード、本書は詳細手順。教材仕様は参照し、複製しない |
| 現在の作業状況・未完了事項・次の一手 | 継続対応する相談エージェントが現在の会話内で管理する。GitHubに日常的な進行記録は作らない |
| 自動テストの具体的検証手順 | テストコード。仕様書には特別な検証条件・守る要件のみ置く |

同じ規則は一か所で管理し、別文書には実在するファイル・見出しへの参照を置く。UI_LAYOUT_SPECとPROJECT_SPECにまたがる事項も責務ごとに分け、同じ規則の正本を二つ作らない。承認済みの個別例外は範囲と理由を固有仕様へ記録し、共通仕様を重複記載しない。既存の重複記録は整理の承認まで残すが、新たな転記・同期義務の根拠にはしない。古い記録から適用範囲を自動的に広げない。

### 5.2 ページ固有仕様書の新設判断と承認

新しいPracticeページを作るだけでは仕様書を新設しない。次の条件がある場合だけ作成を検討する。

- A：共通UI・録音・状態保持・表示・判定などからの重要な例外。
- B：コードからは判断できない教育上の重要な制約。維持する文型の理由、意味・ニュアンスの区別、文法的に可能でも教材上認めない表現、学習段階の特別な制限など。
- C：選択と録音結果の特殊な対応、独自判定、複数行の特殊な保持など、共通部品では説明できない複雑な固有設計。
- D：設計理由を残さないと将来の担当者が誤って変える危険の高い判断。

該当しても直ちに独立文書を作らない。既存共通仕様で扱えるか → 既存のページ群仕様へ追記できるか → 短いコードコメントで足りるか → 独立文書が本当に必要か、の順で判断する。

独立文書が必要なら、編集前に「新設理由／記録する重要な制約／既存文書では管理できない理由／提案ファイル名」を報告し、作成者の承認後に作る。AIは独断で新設しない。作成者が明示的に新設を指示した場合は追加承認を求めない。

### 5.3 記録する内容・記録しない内容

記録するのは、学習目標・重要な文型制約、意味やニュアンスの教育上の判断、共通仕様からの例外と理由、特殊な状態遷移／判定、不変条件、特別な検証条件。

記録しないのは、Drill／Exampleの全設問、現在の動詞・目的語・語彙一覧、タイトル・説明文・Notice全文、選択肢・ラベルの全リスト、コードで直接分かる画面構成、実装を文章へ置換した説明、日々の変更履歴。特定の語や文言そのものが重要な制約なら、その理由と必要最小限の例だけを記録できる。現在の実装の記録と将来も維持すべき制約を区別する。

### 5.4 更新・統合・整理・廃止

設計原則、固有の重要制約、例外、特殊機能／状態遷移が変わった場合、または文書の誤り・矛盾を見つけた場合は、該当する正本を更新する。

設問の追加削除・順序変更、語彙差替え、タイトル／説明文／Noticeの表現変更、微小なレイアウト調整、既存仕様どおりに戻す通常の不具合修正は、原則として仕様書更新不要。ただし重要制約自体に影響すれば必要部分を更新する。コード変更と仕様書更新を機械的に連動させない。

同じ規則がページ固有仕様で繰り返される場合は共通仕様への統合を検討するが、似ているだけで動作が異なるものを無理に統合しない。適用範囲が変わる統合は事前承認を得る。

肥大化した文書は、コード重複 → 他文書重複 → 古い実装状態 → 解決済みの一時問題 → 同じ規則の繰返し、の順で整理し、重要制約を残す。固有制約がなくなれば廃止を提案する。既存仕様書の廃止・統合・大幅削除は、対象と残す情報を提示し、作成者の事前承認後に実施する。履歴・検証根拠の保全方法も示す。

### 5.5 通常変更時の整合性確認と報告

「仕様書が最新」とは、実装と記載された設計原則・制約・例外が矛盾せず、重要な未記録事項がないこと。設問・文言・語彙の全文一致ではない。

各変更の完了前に差分が共通仕様、ページ固有制約、例外、学習目標／文法判断、状態保持・判定・録音等の要件、既存文書の正確性へ影響するか確認する。関係する文書だけを読み、毎回全仕様書を読み直さない。影響なしなら更新不要、影響ありなら該当正本を更新する。有効な仕様に反する変更を文書の書換えで既成事実化せず、作成者へ確認する。

完了報告へ差分に基づく **更新不要／更新済み／要確認** を添える。更新しただけで実装整合を確認できていない場合は確認済みと報告しない。要確認は矛盾・判断待ちの内容を記す。

### 5.6 ページ作業完了宣言時の仕様整合性監査

開始条件は本書「2. 作業・保存・検証」の[ページ作業完了とページ全体テスト](#ページ作業完了とページ全体テスト2026-11-04確定2026-11-14整理)に従う。作成者の宣言で開始するページ全体テストの一部として、最新実装・関連共通仕様・対象ページ／ページ群仕様・重要制約・未解決事項を照合する。AIは作成者の宣言なしにページ作業完了を独自に宣言しない。別途明示的テスト指示には従う。

確認項目は、実装との矛盾、古い実装状態の現行扱い、廃止機能の残存、新たな重要制約／例外の未記録、規則の重複管理、参照先の実在・リンク切れ、文書が実装の複製へ戻っていないか。コードとの機械的全文一致は求めない。

矛盾は次で分類する。

| 分類 | 判断と対応 |
| --- | --- |
| A：文書が古い | 実装が承認済み変更を反映していることを確認し、古い記述を削除・更新。大幅整理は5.4の承認手順に従う |
| B：実装が有効な仕様に違反 | 重要制約は維持し、不一致を報告。実装に合わせて文書を書き換えない |
| C：正否・承認・意図が不明 | 作成者に確認し、仕様・実装を独断で変更しない |

### 5.6.1 完了時の検証資産・一時実装の整理（全Practice共通／2026-11-06確定）

ページ作業完了宣言後の対象ページの全体テスト・仕様整合性監査では、現行実装・承認済み教材／仕様・関連自動テストを照合し、次の整理を必須とする。

- 旧教材・旧キュー・廃止済み設問等を前提とするテスト期待値を特定する。現行仕様でも必要な回帰テストは期待値を更新して維持し、現行仕様で検証対象が存在しないテストだけを削除する。失敗を隠すために期待値を無条件で削除・緩和しない。
- 対象ページに残る暫定表示・試験機能・デバッグ情報・一時検証コード・不要な生成物や参照・廃止機能の残存を確認し、現行の機能・教材・テストに不要と確認できたものを整理する。不要と確認できないものは独断で削除しない。
- 関連仕様書の古い実装状態・解決済みの一時事項は5.4に従い整理し、必要な設計制約・検証根拠・有効な回帰防止策を保持する。文書の廃止・統合・大幅削除は既存の事前承認手順を守る。
- 整理で影響する範囲のテストを再実行し、削除・更新した対象、理由、結果、判断待ち・未確認の項目を最終報告する。共有コード・他ページ・歴史的証跡へ影響する削除や意図が不明な資産は作成者に確認し、対象ページ外の無断整理を行わない。

この確認・整理は全Practiceページに共通する完了時の作業であり、特定ページだけの追加条件ではない。制作途中は引き続き変更箇所の限定検証とし、作業完了の宣言なしに全体整理・包括テストを開始しない。

### 5.7 ページ全体テスト終了時・変更確定

不具合修正後は仕様書への影響を再判定し、必要な更新と影響範囲の再検証を終えて最終整合性を確認する。未解決の仕様矛盾があればページ全体を完全合格にしない。一方、有効仕様との矛盾がなく将来の文書改善案だけが残る場合は合格を妨げない。

必要な仕様書更新は関連コードと整合する同じ作業単位でGitHubへ確定する。未確定設計を承認済み仕様へ混ぜず、未解決としてユーザーへ報告する。作業状況の保存だけを目的とするCommitやPushは行わない。

毎回全ページを再監査する必要はない。変更内容に応じた影響範囲を検証し、対象・検証条件・結果・未確認事項を作業報告に示す。

### 5.8 共通仕様の新設・変更時の適合監査と是正完了義務（2026-11-07確定）

共通仕様の新設・変更・適用範囲拡大は、文書登録だけで既存実装への適用を完了したことにならない。仕様の確定と適用・検証を以下の独立した工程として扱い、全Practice共通規則は原則として全対象ページに適用する。特定のページ群のCSSを共有している事実は、共通仕様の対象をそのページ群に限定する理由にならない。

1. **影響範囲の棚卸し**：共通仕様を新設・変更した担当者は、対象となる全ページ・Example／Drill・共通部品・ページ固有の上書き・既存テストを列挙する。既存実装の適合状況を調べ、未確認を適合済みと扱わない。ページ固有の承認済み例外は、理由と範囲を照合する。
2. **状態の分離**：少なくとも「仕様登録済み」「影響調査済み」「実装対応済み」「再検証済み」「ユーザー実機確認済み」を別々に記録する。文書更新やPush、デプロイ成功のみで後続工程を完了扱いしない。未対応・未検証箇所と検証条件を作業報告で明示する。GitHubに日常的な進行状況の記録を作らない。
3. **不適合の是正**：適合検査で確認した不適合は、原則として修正対象とし、対象を特定して修正する。共通部品・共通CSSでの是正を優先するが、教材・会話の構造や機能が異なるページへ同じDOMや段組みを強制しない。別の変更や新たな独立作業に移る前に、既存変更の確定／保留と残課題を明示する。
4. **再検証と完了条件**：修正後は対象箇所だけでなく共有変更の影響を受けるページを、同じ条件と境界条件で再測定する。必要な回帰テストを追加・更新し、実行結果、未実施範囲、既知の失敗を区別する。対象範囲の確認済み不適合が解消し、必要な検証に合格して初めて「適合対応完了」とする。未修正・未検証が残る場合は部分完了／保留と明記し、完了と偽らない。
5. **例外・判断待ち**：教育上の意図された改行、アクセシビリティ、狭幅での操作性など、共通原則と異なる配置が不可欠な場合は、対象・理由・測定根拠・代替案を示して作成者の承認を得る。理由不明の旧ブレークポイントやページ群限定の実装慣行を無条件で例外化しない。判断待ちは未解決のまま記録する。
6. **検証の起動範囲**：共通仕様の新設・変更では、まず全対象への影響調査を必須とする。ページ横断の実ブラウザ検査・是正は、作成者から今回のように明示的な監査／修正指示があった場合、または既存の「ページ作業完了」条件に達した場合に実施する。無指示で全ページテストを一斉開始しない。個別修正は変更箇所と実際の影響範囲を限定して検証し、共通CSS等の変更により全対象へ影響する場合はその範囲を検証する。

**制定時の対象事例（2026-11-07）**：本節制定時の具体例として、内容幅に基づく折り返し判定に関し、全11 PracticeページのExample／Drill適合検査、およびPractice 8.2 Drillの「じゅぎょう／はなす」の後で「🔊きく」が余裕のある幅でも別行になる現象が調査対象事例として記録された。これらは制定当時の背景事例であり、現在の解決状況は未確認である。この記録は制定当時の背景資料に限られ、現在の未完了作業や全11ページ監査の自動開始指示ではない。現在の作業範囲はユーザーの最新指示と現行仕様を基準に判断する。
