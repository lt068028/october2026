# 3環境リレー運用
版：2026-11-01.1

## 原則
- 合言葉は **「サービス切り替え」**。対象リポジトリを開いた状態で受けたら開始フローを実行し、支障がなければ再確認を求めず再開する。新規会話で合言葉がなくても最初の編集前に実行する。
- GitHub上の main が確定成果の唯一の共通基準。origin/main は最後の取得結果なので、取得前に最新と断定しない。
- LT・INFO・Codexは順番に作業する。LTとINFOは独立した別アカウントで、利用枠も個別確認する。担当変更はユーザーの切り替え指示で成立する。前担当は復帰しても自動再開・Pushしない。
- **クラウド優先・PCローカル編集禁止（2026-11-04追加）**：新規のコード・文書編集はCodex Cloud、Antigravity Remote Agents、権限のあるGitHub API等で実施し、PC上の作業ツリーを変更しない。Codex CLI通常モード、Antigravity Local／Remote Control等のローカル編集モードを自動的に使わない。クラウド内の一時ファイルは許容するが、GitHubのmainまたは途中保存用リモートブランチに反映されるまでは他サービスへの引き継ぎ可能と扱わない。クラウド機能・権限が利用不可なら編集前に報告し、ユーザーの明示許可なしにローカル編集へフォールバックしない。開始時には作業環境がCloud／Remote Agent／GitHub直接編集のいずれかを確認し、旧ローカル環境に残る未Push変更の存在を無視・破棄しない。
- **ローカル変更の未Push放置禁止と即時コミット・Push原則（2026-11-01改定）**：ローカル領域（Antigravity等）でファイルを編集した場合、トークン切れ・会話切断・環境切り替えによって未Push変更がローカルに孤立して他環境から回収不能になることを防ぐため、**編集から構文検証・コミット＆Pushまでを不可分（アトミック）な一連の処理として即座に完了させる**。未Push変更を残したままユーザーへの質問・相談・会話持ち越しを行わない（相談・提案は編集前に行うか、Push完了後に行う）。
- Done命令を必須にしない。突然停止を前提に作業中から保存する。ローカル保存、コミット、リモート保存成功を区別する。
- force push（--force-with-leaseを含む）、reset --hard、git clean等の無断破棄は禁止。同期でマージコミットを作らず、履歴分岐を無断でmerge/rebase/resetにより解消しない。stashで不明な変更を自動的に隠さない。

## GitHub作業・PR運用方針（2026-11-12確定）

**基本原則：作業管理を必要以上に複雑にしない。**

1. 原則として、1つの作業テーマにつき1つのPRを使用する。
2. 可能な限り、現在の作業を検証・完了してから次のテーマに着手する。
3. 同一テーマの修正・追加検証は、原則として既存の作業ブランチとPRで継続する。
4. 新しいPRは、独立した変更として管理する合理的な理由がある場合に限って作成する。
5. 並行作業や統合PRが必要な場合は、作成前に目的・必要性・既存PRとの関係を説明し、ユーザーの承認を得る。
6. Previewでの確認とProductionへの反映を区別し、マージ・本番反映はユーザーの明示的な承認後に行う。
7. 完了済みのPRは整理し、不要なPRを長期間残さない。ただし、未統合の変更を失わないことを確認する。

**目的：** 安全性を維持しながら、管理対象となるブランチ・PR・作業環境の数を最小限にする。

この方針は日本語・ドイツ語の開発双方に適用する。言語別に必ずPRを分離するという意味ではない。既存の未完了PRを無断で閉じず、統合先と保存済み変更を確認してから整理する。

## 1. 開始フロー（二段階読込）
1. ローカルのAGENTS.mdを入口に、対象リポジトリ・origin・現在のブランチ・git status（未追跡含む）・未Pushコミットを確認する。秘密情報を表示しない。
2. git fetch originを行う。Codexの実行環境がコマンド単位のネットワーク権限を提供する場合、通信権限不足ではその正規の仕組みで再試行する。プロキシ無効化・迂回は行わない。失敗した場合は最新との一致を未確認と報告する。認証先・URL・認証設定を無断変更しない。
3. mainがクリーンかつローカルだけのコミットがなければ git pull --ff-only origin main で同期し、HEADと取得後のorigin/mainの一致を確認する。
   - 不明なローカル変更、未Pushコミット、分岐があれば、保全してハッシュ・差分概要を報告し、同期・編集を保留する。調査は可能。
   - クラウドのwork等、サービス指定の作業ブランチは名前だけで異常としない。最新mainを起点としているか確認する。未完成作業の再開は下記復旧手順を使う。
4. 取得後の最新AGENTS.md、本書、docs/PROJECT_SPEC.md、docs/HANDOVER.mdを明示的に読み直す。同期できない場合は取得済みorigin/mainの文書をgit show等で参照し、作業ツリーが同期済みとは扱わない。会話開始時の古い自動読込だけに頼らない。
5. 担当環境・利用アカウント・モデル・利用枠残量とリセット日時を確認する。取得不可ならユーザー確認を依頼する。利用枠不明でも安全な調査・保存は進め、大きな新規作業は確認まで保留する。
6. 次の開始報告を行う。未了事項から小作業を選び、正常なら続行する。次の作業が不明なら推測せず質問する。

開始報告：
- 担当環境：
- 共通ルール版／取得したmainのコミットID：
- 作業ブランチ／HEAD／ローカル状態：
- 引き継ぎ記録・途中保存の確認：
- 利用枠（確認日時・残量・リセット日時／取得不可・確認待ち）：
- 今回の小作業・検証と保存の区切り：

## 2. 作業中の保存・利用枠確認
- 小作業ごとに差分と仕様への影響（本書「8. 仕様書管理と継続的整合性確認」）を確認し、HANDOVERの現在状態を必要最小限更新してコミット・Pushする。作業全体の完了まで記録を先送りしない。ローカル編集後は確実にPushまで完了させ、未Push変更を残したまま質問・確認待ち・会話終了を行わない。
- **ページ作業完了と全体テスト（2026-11-04確定）**：制作中は変更箇所に必要な限定検証のみ行い、ページ全体の包括テストを繰り返さない。作成者が「ページ作業完了」と宣言したら対象ページの全体テストを開始する。制作終了と検証完了を区別し、Codexは独自に宣言・開始しない。別途明示的なテスト指示には従う。不具合修正後は影響範囲を再検証する。既存の限定検証条件・安全制約は維持し、定義・確認項目・結果報告・共通タッチ検証はPROJECT_SPEC「全Practice共通：ページ作業完了とページ全体テスト」に従う。
- 小作業3件完了時、または大きな処理の着手前に利用枠を再確認する。取得できなければ「残量を取得できないため定期確認」と明示してユーザーへ依頼する。検知していないのに上限接近を断定しない。同じ確認を重複して依頼しない。
- 暫定閾値：関係する利用枠の残量30％以下で作業を細分化、20％以下または上限警告で終了準備。各枠のうち作業を制限する枠を使い、実績で調整する。残量の割合が表示されない場合は数値を捏造しない。
- 利用枠と会話コンテキストは別管理。コンテキスト逼迫時も状況を保存してから圧縮・新規会話を検討する。
- 確認待ちでも保存を優先する。返答なしを利用枠十分・承認済みと扱わない。
- ルールだけでは無操作中の監視、正確な時刻通知、上限直前の検知を保証しない。タイマー・フック・監視・preflightスクリプトは別途実装と検証が必要。
- 改行・文字コードの一括変換、無関係な整形をしない。ツールの必要バージョンを共有し、環境固有の絶対パスを埋め込まない。

確認先（UI・版・プランにより異なる）：
- Codex：使用量 https://chatgpt.com/codex/settings/usage ／CLIの /status、/statusline。
- Antigravity：Settingsのモデル利用枠／CLIの /usage（/quota）、コンテキストは /context。
- 公式資料：https://developers.openai.com/codex/pricing 、https://developers.openai.com/codex/cli/slash-commands 、https://antigravity.google/docs/plans 、https://antigravity.google/docs/cli/commands/usage 、https://antigravity.google/docs/cli/commands/context 。

## 3. 終了・引き継ぎフロー
1. 新規作業を止め、進行中の処理を確認する。バックグラウンドの編集・Pushが残らないよう安全に停止し、停止不能なら報告する。
2. 差分・秘密情報・不要ファイルを確認する。終了直前は追加実装や長時間テストより保存を優先し、未検証を明記する。
3. HANDOVERの現在状態を更新する。仕様書の更新要否は本書「8. 仕様書管理と継続的整合性確認」で判断し、必要な正本のみ更新する。
4. 作業中の変更は原則として当該テーマの既存作業ブランチへPushし、検証・Preview・ユーザー承認後にPRを通してmainへ反映する。未完成・検証未了は当該作業ブランチ、または必要時のみ relay/<環境>-<日時> 等の途中保存用ブランチに保全する。途中保存は未確定成果でありmainの代わりにしない。mainへの直接PushやPRマージ・Production反映はユーザーの明示的承認なしに行わない。
5. Push後は再取得等で送信先とコミットIDを照合し、意図しないローカル残作業の有無を確認する。mainに反映する直前に他環境の更新があれば停止して照合する。自動マージ・強制Pushをしない。
6. 「引き継ぎ可能（GitHub保存確認済み）／ローカル保存のみ／保存失敗」を報告する。実装、自動検証、ユーザー実機確認、CI・公開反映は分ける。

途中保存用ブランチのHANDOVERも更新する。mainのHANDOVERだけに依存せず、受取側はリモートのrelay/*とmain以外の前担当ブランチを確認する。プレビュー公開やCIが動く可能性があるので機密情報を含めず、途中保存で本番公開されない設定を確認する。

## 4. 突然停止からの復旧
- 終了報告がなければ完了・Push済みと推測しない。最新main、HANDOVER、リモート途中保存ブランチとその記録・差分を確認し、必要な検証後に再開する。
- 途中保存ブランチを継続する場合、mainとの差・親コミット・変更内容を確認する。分岐の無断解消は禁止。
- 未Push変更は他環境から回収できない。「未回収」と明記し、GitHub保存地点から進められる範囲と分ける。
- 前環境復帰時は未保存差分を保全して現在のmainと比較し、必要分だけ回収する。古い状態のままPushしない。

## 5. 引き継ぎ記録の書式
HANDOVERの冒頭に「現在のリレー状態」を置き、履歴を消さず更新する。
- 更新日時（タイムゾーン付き）／担当環境：
- 状態：作業中・引き継ぎ可能・判断待ち・ローカル保存のみ・保存失敗
- 課題／開始時mainのコミットID／作業ブランチ：
- 完了・未完了／変更ファイル：
- 自動検証：コマンド、結果、失敗・未実行：
- ユーザー実機確認／CI／デプロイ：
- 次の具体的操作／判断待ち／未回収作業：
- 保存先：ブランチ（最終コミットIDはGit履歴・終了報告で確認。自分自身のコミットIDを埋め込むための再コミットは不要）

## 6. 各サービスの読込確認
- 共通本文を3環境へ複製しない。各サービスの自動読込入口からAGENTS.mdを参照する。
- Codex・LT・INFOそれぞれ、初回導入時は最新ルールを取得し、新規会話で「サービス切り替え」を送る。取得前の古い入口には新ルールがまだ存在しない可能性がある。
- AGENTS.mdの自動読込、最新取得後の再読込、開始報告を環境別に実機確認して初めて読込設定完了とする。自動読込できなければ、その環境の常時適用設定に参照指示を追加する。
- ファイル名だけで全サービスの自動適用を保証しない。スクリプトも迂回できるため誤操作ゼロとは扱わない。

## 8. 仕様書管理と継続的整合性確認

本節を文書管理手順の唯一の正本とし、Codex・Antigravity LT／INFOなど、すべてのAI開発環境へ恒久適用する。実装内容の転記ではなく、将来も守る設計原則・制約・例外を管理する。

### 8.1 文書の種類・責務・正本

| 情報 | 正本と責務 |
| --- | --- |
| 現在の設問・教材・語彙・表示文言・選択肢 | ページの実装コード |
| 共通機能・動作・設計 | [PROJECT_SPEC.md](PROJECT_SPEC.md)：音声・録音・STT/TTS・状態保持・表記／教材の基本原則・ページ全体テスト基準 |
| 共通表示・操作配置・レイアウト | [UI_LAYOUT_SPEC.md](UI_LAYOUT_SPEC.md)：PROJECT_SPECの機能要件を前提とする共通UI契約 |
| ページ／密接なページ群の重要な制約 | 承認済みの該当ページ固有仕様書。教育上の理由・重要な例外・複雑な固有設計・不変条件を扱う |
| AIの作業手順・同期・文書管理 | [AGENTS.md](../AGENTS.md)は入口・必須ガード、本書は詳細手順。教材仕様は参照し、複製しない |
| 未完了事項・未解決不具合・検証状況・引き継ぎ状態 | [HANDOVER.md](HANDOVER.md) |
| 自動テストの具体的検証手順 | テストコード。仕様書には特別な検証条件・守る要件のみ置く |

同じ規則は一か所で管理し、別文書には実在するファイル・見出しへの参照を置く。UI_LAYOUT_SPECとPROJECT_SPECにまたがる事項も責務ごとに分け、同じ規則の正本を二つ作らない。承認済みの個別例外は範囲と理由を固有仕様へ記録し、共通仕様を重複記載しない。既存の重複記録は整理の承認まで残すが、新たな転記・同期義務の根拠にはしない。古い記録から適用範囲を自動的に広げない。

### 8.2 ページ固有仕様書の新設判断と承認

新しいPracticeページを作るだけでは仕様書を新設しない。次の条件がある場合だけ作成を検討する。

- A：共通UI・録音・状態保持・表示・判定などからの重要な例外。
- B：コードからは判断できない教育上の重要な制約。維持する文型の理由、意味・ニュアンスの区別、文法的に可能でも教材上認めない表現、学習段階の特別な制限など。
- C：選択と録音結果の特殊な対応、独自判定、複数行の特殊な保持など、共通部品では説明できない複雑な固有設計。
- D：設計理由を残さないと将来の担当者が誤って変える危険の高い判断。

該当しても直ちに独立文書を作らない。既存共通仕様で扱えるか → 既存のページ群仕様へ追記できるか → 短いコードコメントで足りるか → 独立文書が本当に必要か、の順で判断する。

独立文書が必要なら、編集前に「新設理由／記録する重要な制約／既存文書では管理できない理由／提案ファイル名」を報告し、作成者の承認後に作る。AIは独断で新設しない。作成者が明示的に新設を指示した場合は追加承認を求めない。

### 8.3 記録する内容・記録しない内容

記録するのは、学習目標・重要な文型制約、意味やニュアンスの教育上の判断、共通仕様からの例外と理由、特殊な状態遷移／判定、不変条件、特別な検証条件。

記録しないのは、Drill／Exampleの全設問、現在の動詞・目的語・語彙一覧、タイトル・説明文・Notice全文、選択肢・ラベルの全リスト、コードで直接分かる画面構成、実装を文章へ置換した説明、日々の変更履歴。特定の語や文言そのものが重要な制約なら、その理由と必要最小限の例だけを記録できる。現在の実装の記録と将来も維持すべき制約を区別する。

### 8.4 更新・統合・整理・廃止

設計原則、固有の重要制約、例外、特殊機能／状態遷移が変わった場合、または文書の誤り・矛盾を見つけた場合は、該当する正本を更新する。

設問の追加削除・順序変更、語彙差替え、タイトル／説明文／Noticeの表現変更、微小なレイアウト調整、既存仕様どおりに戻す通常の不具合修正は、原則として仕様書更新不要。ただし重要制約自体に影響すれば必要部分を更新する。コード変更と仕様書更新を機械的に連動させない。

同じ規則がページ固有仕様で繰り返される場合は共通仕様への統合を検討するが、似ているだけで動作が異なるものを無理に統合しない。適用範囲が変わる統合は事前承認を得る。

肥大化した文書は、コード重複 → 他文書重複 → 古い実装状態 → 解決済みの一時問題 → 同じ規則の繰返し、の順で整理し、重要制約を残す。固有制約がなくなれば廃止を提案する。既存仕様書の廃止・統合・大幅削除は、対象と残す情報を提示し、作成者の事前承認後に実施する。履歴・検証根拠の保全方法も示す。

### 8.5 HANDOVERの運用

現在の作業状態、未完了事項、未解決不具合、検証済み／未検証範囲、次の担当者の注意事項を優先する。小作業の区切りでは現在状態を簡潔に更新し、実装全文や仕様の複製・長文の変更履歴を毎回追加しない。

解決済みを現在の不具合として残さず、過去の検証は対象コミット・条件とともに履歴として区別する。重要な根拠・追跡可能性を失う削除は行わず、必要なら保管・参照方法を提案する。今回の登録では過去履歴を一括削除しない。未Push放置禁止・途中保存を含む既存リレー運用を維持する。

### 8.6 通常変更時の整合性確認と報告

「仕様書が最新」とは、実装と記載された設計原則・制約・例外が矛盾せず、重要な未記録事項がないこと。設問・文言・語彙の全文一致ではない。

各変更の完了前に差分が共通仕様、ページ固有制約、例外、学習目標／文法判断、状態保持・判定・録音等の要件、既存文書の正確性へ影響するか確認する。関係する文書だけを読み、毎回全仕様書を読み直さない。影響なしなら更新不要、影響ありなら該当正本を更新する。有効な仕様に反する変更を文書の書換えで既成事実化せず、作成者へ確認する。

完了報告へ差分に基づく **更新不要／更新済み／要確認** を添える。更新しただけで実装整合を確認できていない場合は確認済みと報告しない。要確認は矛盾・判断待ちの内容を記す。

### 8.7 ページ作業完了宣言時の仕様整合性監査

開始条件は[PROJECT_SPECの全Practice共通：ページ作業完了とページ全体テスト](PROJECT_SPEC.md#全practice共通ページ作業完了とページ全体テスト2026-11-04確定)に従う。作成者の宣言で開始するページ全体テストの一部として、最新実装・関連共通仕様・対象ページ／ページ群仕様・重要制約・未解決事項を照合する。Codexは独自に宣言・開始しない。別途明示的テスト指示には従う。

確認項目は、実装との矛盾、古い実装状態の現行扱い、廃止機能の残存、新たな重要制約／例外の未記録、規則の重複管理、参照先の実在・リンク切れ、文書が実装の複製へ戻っていないか。コードとの機械的全文一致は求めない。

矛盾は次で分類する。

| 分類 | 判断と対応 |
| --- | --- |
| A：文書が古い | 実装が承認済み変更を反映していることを確認し、古い記述を削除・更新。大幅整理は8.4の承認手順に従う |
| B：実装が有効な仕様に違反 | 重要制約は維持し、不一致を報告。実装に合わせて文書を書き換えない |
| C：正否・承認・意図が不明 | 作成者に確認し、仕様・実装を独断で変更しない |

### 8.7.1 完了時の検証資産・一時実装の整理（全Practice共通／2026-11-06確定）

ページ作業完了宣言後の対象ページの全体テスト・仕様整合性監査では、現行実装・承認済み教材／仕様・関連自動テストを照合し、次の整理を必須とする。

- 旧教材・旧キュー・廃止済み設問等を前提とするテスト期待値を特定する。現行仕様でも必要な回帰テストは期待値を更新して維持し、現行仕様で検証対象が存在しないテストだけを削除する。失敗を隠すために期待値を無条件で削除・緩和しない。
- 対象ページに残る暫定表示・試験機能・デバッグ情報・一時検証コード・不要な生成物や参照・廃止機能の残存を確認し、現行の機能・教材・テストに不要と確認できたものを整理する。不要と確認できないものは独断で削除しない。
- 関連仕様書・HANDOVERの古い実装状態・解決済みの一時事項は8.4／8.5に従い更新し、履歴・検証根拠・有効な回帰防止策を保持する。文書の廃止・統合・大幅削除は既存の事前承認手順を守る。
- 整理で影響する範囲のテストを再実行し、削除・更新した対象、理由、結果、判断待ち・未確認の項目を最終報告する。共有コード・他ページ・歴史的証跡へ影響する削除や意図が不明な資産は作成者に確認し、対象ページ外の無断整理を行わない。

この確認・整理は全Practiceページに共通する完了時の作業であり、特定ページだけの追加条件ではない。制作途中は引き続き変更箇所の限定検証とし、作業完了の宣言なしに全体整理・包括テストを開始しない。

### 8.8 ページ全体テスト終了時・保存・環境切替

不具合修正後は仕様書への影響を再判定し、必要な更新と影響範囲の再検証を終えて最終整合性を確認する。未解決の仕様矛盾があればページ全体を完全合格にしない。一方、有効仕様との矛盾がなく将来の文書改善案だけが残る場合は合格を妨げない。

必要な文書更新は関連コードと整合する同じ作業単位でGitHubへ確定する。未確定設計を承認済み仕様へ混ぜず、未解決として報告し、未Pushを残さない。

環境切替では、仕様書更新が必要な未完了事項、実装との未解決矛盾、最後の監査の対象コミット・範囲・結果を引き継ぐ。受取側は最新mainと引き継ぎを読み、未解決を確認なしに解決済みとしない。毎回全ページを再監査する必要はない。各環境の入口はAGENTSから本節を参照し、別コピーを作らない。設定ファイル保存と、新規会話での自動読込確認は区別する。

ページ全体テストの最終報告には、対象ページ・検証コミット、参照仕様書、**仕様整合性：合格／不合格／未確認**、古い記述／矛盾の有無、更新文書、残課題を含める。「合格」は有効仕様との矛盾がなく必要な更新が完了した場合のみ使う。

本運用ルールの登録と将来の監査実施を区別する。登録だけでは、いずれのページの「ページ作業完了」宣言やページ全体テスト実施としても扱わない。

### 8.9 共通仕様の新設・変更時の適合監査と是正完了義務（2026-11-07確定）

共通仕様の新設・変更・適用範囲拡大は、文書登録だけで既存実装への適用を完了したことにならない。仕様の確定と適用・検証を以下の独立した工程として扱い、全Practice共通規則は原則として全対象ページに適用する。特定のページ群のCSSを共有している事実は、共通仕様の対象をそのページ群に限定する理由にならない。

1. **影響範囲の棚卸し**：共通仕様を新設・変更した担当者は、対象となる全ページ・Example／Drill・共通部品・ページ固有の上書き・既存テストを列挙する。既存実装の適合状況を調べ、未確認を適合済みと扱わない。ページ固有の承認済み例外は、理由と範囲を照合する。
2. **状態の分離**：少なくとも「仕様登録済み」「影響調査済み」「実装対応済み」「再検証済み」「ユーザー実機確認済み」を別々に記録する。文書更新やPush、デプロイ成功のみで後続工程を完了扱いしない。未対応・未検証箇所、検証条件、担当・次の対応をHANDOVERへ簡潔に記録する。
3. **不適合の是正**：適合検査で確認した不適合は、原則として修正対象とし、対象を特定して修正する。共通部品・共通CSSでの是正を優先するが、教材・会話の構造や機能が異なるページへ同じDOMや段組みを強制しない。別の変更や新たな独立作業に移る前に、既存変更の確定／保留と残課題を明示する。
4. **再検証と完了条件**：修正後は対象箇所だけでなく共有変更の影響を受けるページを、同じ条件と境界条件で再測定する。必要な回帰テストを追加・更新し、実行結果、未実施範囲、既知の失敗を区別する。対象範囲の確認済み不適合が解消し、必要な検証に合格して初めて「適合対応完了」とする。未修正・未検証が残る場合は部分完了／保留と明記し、完了と偽らない。
5. **例外・判断待ち**：教育上の意図された改行、アクセシビリティ、狭幅での操作性など、共通原則と異なる配置が不可欠な場合は、対象・理由・測定根拠・代替案を示して作成者の承認を得る。理由不明の旧ブレークポイントやページ群限定の実装慣行を無条件で例外化しない。判断待ちは未解決のまま記録する。
6. **検証の起動範囲**：共通仕様の新設・変更では、まず全対象への影響調査を必須とする。ページ横断の実ブラウザ検査・是正は、作成者から今回のように明示的な監査／修正指示があった場合、または既存の「ページ作業完了」条件に達した場合に実施する。無指示で全ページテストを一斉開始しない。個別修正は変更箇所と実際の影響範囲を限定して検証し、共通CSS等の変更により全対象へ影響する場合はその範囲を検証する。
