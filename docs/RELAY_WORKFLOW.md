# October2026 — 作業・GitHub運用手順

> **版：2026-11-18.1**
>
> **運営前提**：個人運営の原則と費用・管理負担の扱いは [`AGENTS.md` §1](../AGENTS.md) を参照する。企業・複数人組織を前提とする工程を追加しない。
>
> **GitHubの用途**：GitHubは成果物の保管・変更・公開に使う。相談役への作業状況の伝達には使わない。

## 原則

役割の意味と割当原則は、[AGENTS.md「この会話における担当範囲」](../AGENTS.md#この会話における担当範囲2026-11-19更新)を正本とする。本書では役割定義を重複記載せず、各役割が行う具体的な作業手順を定める。

- GitHubの `main` を、確定したコード・仕様書・テスト等の成果物の基準とする。GitHubは成果物の変更履歴と公開のために使い、会話の進捗・未完了事項・次の一手を保管する場所にはしない。
- 作業状況・判断の経緯・未完了事項は、継続対応する相談役が現在の会話内で管理する。ローカル環境を利用した担当者は、ローカルに残る変更・作業状態を把握・記録し、担当交代・中断時に次の担当者が継続できる情報を現在の会話内で共有する。`HANDOVER.md`、日常作業ログ、状況だけを記録するCommit、引き継ぎ専用ブランチを新設・更新しない。
- **使用可能な作業環境と編集先の確認**：コード・文書編集は、Codex Cloud、Antigravity Remote Agents、Antigravity Remote Control、権限のあるGitHub API等から、実際に利用できる適切な環境を選んで行う。ローカル環境の利用許可条件は `AGENTS.md` に従う。ローカル利用許可が得られない場合は、許可済みの別環境またはGitHub API等で実施可能か判断し、できない場合は作業を開始せず報告する。Antigravity Remote Controlから操作するChromebookのChromeOS Linux／Crostini上のAntigravityアプリの作業ツリー `/home/lt068028/october2026` はローカル環境であり、クラウド上の作業ツリーではない。ここに記載した環境情報は利用許可を意味しない。
- 作業環境を問わず、対象リポジトリ・実際の作業ツリー・ブランチ・基準コミット・未コミット／未追跡変更を確認する。不明な変更を上書き・破棄しない。ローカル作業ツリーでは、既存差分がないことを確認してから最新 `main` と同期する。既存差分がある場合は先に内容と出所を確認し、無断でstash・reset・clean・上書きを行わない。GitHub APIで直接編集する場合も、更新対象ファイルの最新内容・SHAを取得してから更新する。
- 役割の担当変更や会話継続への備えだけを理由にPushやブランチ作成を行わない。
- force push（--force-with-leaseを含む）、reset --hard、git clean等の無断破棄は禁止。履歴分岐を無断でmerge/rebase/resetにより解消しない。stashで不明な変更を自動的に隠さない。

## 相談役による指示書の作成・区分（2026-11-16制定）

本節は、相談役が分析役または実装担当へ渡す個別指示書の作成方法を定める。個別指示書は原則としてその都度会話内で作成し、タスクごとの指示書・進捗記録をGitHubへ保存しない。本節の共通ルールだけを本書で管理する。

### 1. 指示書のタイトル

タイトルは必ず次の3要素をこの順で記載する。

`区分｜タスク名｜今回の具体的な作業概要`

区分は次のいずれか一つとし、表記を統一する。

- `分析調査`
- `実装Planあり`
- `実装Planなし`

タイトルにはタスクを識別する名称と、何を調査・実装するかが分かる概要を記載する。詳細な条件・手順はタイトルへ詰め込まず、本文に記載する。

### 2. 本文の固定フォーマット

タイトルの下には、次の7項目を必ずこの順序で配置する。該当する情報がない項目も省略せず、`該当なし` と明記する。各項目の中には、タスクに必要な具体的情報を記載する。

1. **目的**：今回解決する問題、確認する疑問、達成する成果を明確にする。
2. **対象・参照先**：対象ページ・機能・ファイル・関連仕様書・参照する基準Commit等を特定する。対象を推測で広げない。
3. **具体的な作業内容**：実施する調査・分析・変更と、必要な手順を具体的に示す。抽象的な「確認する」「適切に修正する」だけで終わらせない。
4. **作業範囲・除外事項**：今回実施する範囲、対象外、禁止事項を明示する。通常運用と異なる作業環境・ブランチ・Preview限定・Commit／Push／公開の制限など、タスク固有の条件もここに記載する。
5. **維持条件**：変更してはならない既存仕様・機能・教材・表示・挙動、変更対象外の範囲を明示する。
6. **検証・完了条件**：今回必要な検証方法・対象・合格条件、および依頼の達成を判断する条件を記載する。検証範囲は依頼と実際の影響範囲に合わせ、無関係な全体テストを一律に追加しない。
7. **報告事項**：今回の作業で報告すべき成果・根拠・変更箇所・検証結果・未確認事項・残件を指定する。

### 3. 共通ルールとの役割分担

- 作業環境の確認、既存差分の保全、GitHubの同期・Commit・Push、仕様書管理、標準的な検証・報告等は、`AGENTS.md` と本書の既存規定に従う。個別指示書へそれらの一般規則を毎回全文転記しない。
- 個別タスクで標準運用と異なる条件を指定する場合は、本文の「作業範囲・除外事項」に明記する。個別指示書の条件と共通規則が矛盾する場合は、最新のユーザー指示を優先し、矛盾が解消できないときは独断で実行せず確認する。
- 本文7項目は固定するが、項目内の説明・箇条書きはタスクに応じて具体化する。固定文を機械的に繰り返すのではなく、作業者が判断を誤らない情報を記載する。

### 4. 区分ごとの作業許可と進め方

#### A. 分析調査

- ユーザーは通常モードのまま指示書を送る。Planモードへの切替は不要。
- 目的は現状確認、原因究明、仕様・実装の整合確認、選択肢比較、実装可否の判断材料の収集等とする。
- 調査・分析は読み取り専用とする。既存ファイルの編集・修正・削除、設定変更、実装、Commit、Pushを行わない。調査のための検証も、プロジェクトの成果物や状態を変更しない方法に限る。
- 報告では、確認できた事実とその根拠、分析上の推定・解釈、未確認事項・制約を区別する。必要に応じて原因・影響範囲・対応案を示す。
- 調査で修正が必要な問題を発見しても、その場で修正せず報告する。次の実装区分や対象範囲はユーザーが選択する。

#### B. 実装Planあり

- ユーザーは `/plan` でPlanモードに切り替えてから指示書を送る。
- まず既存実装・関連仕様を確認し、実装Planを作成する。Planには、対象ファイル・対象箇所、変更方針・手順、影響範囲と依存関係、維持条件、必要な検証方法・完了条件を含める。重要な不確実性・判断が必要な点があれば明示する。
- Plan作成段階では実装・編集・削除・Commit・Pushを行わず、Planを提示して停止する。
- **Planの作成・自動レビュー・画面上の承認操作は、ユーザーによる実装指示の代わりにならない。ユーザーが明示的に実装を指示するまで実装を開始しない。** Global／ProjectのPlan Review Policyの設定によって、この条件を省略しない。
- 実装開始後は、ユーザーが確認したPlanの範囲に従う。実装上の理由で対象・方式・影響範囲を変える必要が生じた場合は、先に変更理由と影響を報告し、必要な判断を得る。Planに含まれない追加作業を独断で行わない。

#### C. 実装Planなし

- ユーザーは通常モードのまま指示書を送る。Planモードへの切替は不要。
- 目的・対象・変更内容・維持条件・完了条件が十分に明確で、限定された範囲で直接実装できる作業に用いる。
- 正式なPlan作成工程は設けないが、実装前に既存コード・関連仕様・対象識別・直接影響範囲を確認する。指示された範囲内で直接実装し、必要な検証を行う。
- 仕様上の矛盾、重大な不明点、想定外の影響拡大、当初の範囲を超える設計判断が必要になった場合は、推測で進めたり独断でPlanありへ切り替えたりせず、状況と選択肢を報告してユーザーの判断を待つ。

### 5. 相談役による区分の選択基準

相談役は、タスクの目的・不確実性・実装の複雑さ・依存関係・影響範囲・設計判断の必要性に基づき、次の基準で区分を選ぶ。

- **分析調査**：まず現状・原因・仕様整合・実装可否を明らかにする必要があり、実装内容や対象範囲をまだ確定できない場合。分析が広範囲・複雑であることだけを理由に実装Planありとはしない。
- **実装Planあり**：実装する目的と大枠の対象は定まっているが、複数の変更の依存関係、共有機能への波及、複数の実装方式、重要な設計判断、影響・リスクの評価など、実装前に計画を確認する価値が高い場合。
- **実装Planなし**：対象・変更内容・維持条件・完了条件が具体的で、実装方法も明確であり、Plan作成による追加価値が小さい限定作業の場合。

変更ファイル数や作業量だけで機械的に区分を決めない。複数ファイルでも同一の明確な変更を適用する作業はPlanなしにできる一方、1つの共有ファイルの変更でも影響が広く設計判断を伴う場合はPlanありが適切となり得る。実装対象や原因自体が未確定なら、実装Planを作る前に分析調査を選ぶ。

相談役は選択した区分に対応するタイトルと本文を作成する。ユーザーは区分を変更でき、ユーザーの明示指定を相談役の選択より優先する。

## GitHub作業・PR／ブランチ運用方針（2026-11-16改定）

**基本原則：`main` を唯一の正式な成果物の正本とし、通常の作業は `main` への直接Commit・Pushで完了する。PRは通常運用に使用しない。**

### 通常運用
1. 通常の作業は、原則として `main` への直接Commit・Pushで完了させる。
2. 相談役・分析役・実装担当は、ユーザーの明示的な指示なく、作業ブランチやPRを作成しない。Preview確認等のためにブランチが必要な場合も、ユーザーが明示的に指定した一時作業に限る。
3. PRはOctober2026の通常工程に含めない。ユーザーが例外としてPRの作成を明示的に指示した場合だけ使用する。
4. 同一テーマの作業を不必要に分割せず、指定範囲の変更・差分・必要な検証を確認して `main` に反映する。
5. Commit・Push前には変更範囲、差分、検証結果を確認し、指定外の変更を混入させない。

### 作業ブランチ・PRの終了と整理
1. 作業ブランチは一時的な作業手段であり、成果物の保管場所や将来の案の倉庫として扱わない。正式な成果物は `main` に置く。
2. ユーザーの指示で作成した一時ブランチは、その用途が終了し、変更が `main` に反映された時点、または作業を断念・終了した時点で削除する。未完了の作業が現に継続中の場合だけ、その作業に必要な期間保持する。
3. `main` に採用されなかった案・比較用実装・診断用実装は、将来再利用できる可能性だけを理由に保存しない。再び必要になった場合は、最新の `main` を基準に新しく作成する。
4. PRを例外的に使用した場合も、PRを作業状況の保管場所としてOpenのまま残さない。ユーザーが採用しないと決めたPR、または目的を終えたPRはCloseし、対応する作業ブランチも不要になり次第削除する。マージ済みPRのGitHub上の履歴は残るが、作業ブランチを維持する理由にはしない。
5. ユーザーが特定のブランチや変更の保存を明示的に指示した場合だけ、その指定範囲を例外として保持する。

### Production反映との関係
- `main` へのPushによってVercel等のProduction自動デプロイが発生する設定の場合、その動作を事前に把握しておく。
- ユーザーからGitHubのmainへの反映を指示された通常作業では、そのPushに伴う自動デプロイを想定される結果として扱う。PRを必須にしたり、同じ指示について二重の承認を求めたりしない。
- ユーザーが明示的にPreview限定・本番反映保留等を指定した場合は、その指定を優先する。
- 本番反映の仕組みが不明な場合は、確認できた範囲と不明点を報告し、事実を推測で補わない。

この方針は日本語・ドイツ語の開発双方に適用する。

## 1. 作業開始時の確認

1. 対象リポジトリが `lt068028/october2026` であることを確認し、作業開始前にGitHubの最新 `main` と対象ファイルの状態を取得する。取得できない場合は、最新状態を確認できていないことを明示する。
2. 作業環境の選択、ローカル利用の許可、編集先・既存差分の確認は、本書「原則」の「使用可能な作業環境と編集先の確認」に従う。
3. 最新の `AGENTS.md`、本書、`docs/PROJECT_SPEC.md`、および今回の作業に関係する仕様書・テスト説明を読む。無関係な文書や全ページの実装を機械的に読み込まない。
4. 作業対象・変更範囲・必要な検証を定める。対象や既存変更の状態が不明な場合は推測で編集せず、確認できた事実と支障を報告する。
5. `main` へ反映する直前に最新状態を再確認する。他の変更が先に入っていれば差分を照合し、既存成果を上書きしない。

開始時に毎回定型の環境情報・進捗報告を要求しない。複雑な作業では、対象・基準コミット・作業範囲・検証方針を必要な範囲でユーザーに示す。

## 2. 作業・保存・検証

- **自動検証の選択**：必要なテスト・検証項目の選択、Node.jsをローカルに導入しない方針、CI実行対象との照合、CI対象外・未検証項目の扱いは、`tests/README.md` §1.4〜§1.6を正本とする。ローカル自動テストを標準要件にせず、Push後のCI確認・結果URL報告は本書§3の手順に従う。CIワークフローの変更は、具体的な変更内容を提示し、ユーザーの承認を得てから実施する。

- 作業単位ごとに差分と関係仕様への影響を確認し、必要な成果物だけを更新する。作業状況を残すためだけの文書変更・Commit・Pushは行わない。
- コード・仕様書等の確定成果は、変更範囲・差分・必要な検証結果を確認して `main` へ直接Commit・Pushする。相談役・分析役・実装担当の判断だけでPRや作業ブランチを作成しない。ユーザーが明示的に指定した一時作業に限りブランチを使用し、用途終了または作業断念後は「GitHub作業・PR／ブランチ運用方針」に従って削除する。PRはユーザーが明示的に指示した場合だけ使用する。

### ページ作業完了と作業範囲に応じた最終確認（2026-11-04確定／2026-11-16整合整理）

#### 1. 用語と宣言者
- **ページ作業完了**：実装担当が必要な教材内容・練習問題・機能・UI・レイアウト等の制作を終えたと判断した状態。テスト合格や不具合がないことを意味しない。
- **ページ全体テスト**：当該ページの広い範囲を包括的に検証する方法。ユーザーの明示指示、依頼された受入条件、または変更がページ全体へ及ぶ場合など、作業範囲上必要なときに選択する。ページ作業完了の宣言だけで自動的に必須とはしない。
- **検証完了**：そのページに必要な検証項目が終了し、必須項目の合格が確認された状態。未実施・未確認・不合格は区別して報告する。
- 宣言するのは実装担当であり、相談役・分析役は独自にページ作業完了を宣言したり、全体テストを開始したりしない。
- 実装担当が「ページ作業完了」と宣言したら、制作を終えたことを受けて必要な最終確認へ移行する。確認対象とテスト範囲は、今回の依頼・変更内容・直接影響を受ける範囲・受入条件に基づいて決める。

#### 2. 開始条件とテスト範囲
- 制作中は、変更箇所と直接影響を受ける範囲の限定検証を行う。
- 制作中に対象ページ全体の包括テストを繰り返さない。
- ページ作業完了後は、少なくとも変更箇所と直接影響を受ける範囲を最終確認する。ページ全体テストは、その広さが依頼・変更の影響範囲または明示された受入条件に含まれる場合に限って実施する。
- ページ全体テストを実施する場合も、他ページや全リポジトリの全テストを自動的に実行する指示ではない。
- ページ固有テストと共通機能・共通CSSの影響範囲を考慮し、変更・影響範囲に対応する必要な検証だけを選択する。変更のない無関係な機能のテストや、すでに確認済みの同一テストを一律に繰り返さない。
- 不具合修正後は、修正箇所と実際の影響範囲を再検証する。
- 全11ページ横断のE2Eテストは、全ページへの影響が想定される場合や全体の総合確認が必要な場合に選択する。1ページの作業完了だけを理由に必須とはしない。
- テストの選択・実行方針は、2026-11-14にユーザー承認された [tests/README.md](../tests/README.md) と整合させる。

#### 3. ページ全体テストの確認範囲
各確認項目の合否は、次の正本に照らして判断する。
- 共通機能・動作要件：`PROJECT_SPEC.md`
- 共通UI・表示・レイアウト：`UI_LAYOUT_SPEC.md`
- ページ固有の教育上の制約・例外：承認済みの該当ページ固有仕様書
- 現在の設問・教材・語彙・表示文言：ページの実装コード
- 自動テストの選択・実行方法：ユーザー承認済みの `tests/README.md`

1. **教材・コンテンツ**
   - Example／Drillの内容
   - 文法・語彙・表記・モデル文・キューの整合性
   - 該当するページ固有仕様との一致
2. **ホバー**
   - 語句と英語訳・ローマ字の対応
   - 表示位置と画面外へのはみ出し
   - 隣接語句・選択欄・録音ボタン等との重なり
   - 折り返しや画面幅変更時の位置ずれ
   - Hover／Display／OFF等、ページで使用する表示モード
3. **レイアウト**
   - 正式サポート対象であるPC・タブレットの表示
   - 文字の折り返し、余白、整列

#### 5. 結果報告

- 合格
- 不合格
- 未実施・未確認
- 対象外

不具合については、原因、影響範囲、修正内容、再検証結果を報告する。
なお、本規定自体の登録や更新を、ページ作業完了・検証完了と扱わない。

## 3. 作業終了・変更確定

1. 新規作業を止め、進行中の処理を確認する。バックグラウンドの編集・Pushが残らないよう安全に停止し、停止不能ならその状態を報告する。
2. 差分・秘密情報・不要ファイルを確認する。未検証箇所や未完了事項を完了扱いしない。
3. 関係仕様書の更新要否を本書「5. 仕様書管理と継続的整合性確認」で判断し、必要な正本だけを更新する。
4. ユーザーの指示範囲に含まれる確定成果は、検証・差分確認後に `main` へ直接反映する。PR／作業ブランチはユーザーが明示的に指定した場合だけ使用する。一時ブランチは用途終了または作業断念後に削除し、未採用案を将来の再利用のために保存しない。
5. Push後は送信先とコミットIDを照合する。Production自動デプロイが関係する場合は、GitHubへの反映・CI・デプロイ・公開ページの実表示をそれぞれ区別する。
6. **CIの一次確認と結果URLの報告**：Push後、実装担当はPushしたCommitに対するGitHub Actions／Checksの状態を一度確認し、確認時点の状態と確認用URLを報告する。実行が完了していれば最終結果と実行URLを、実行中・待機中であればその状態と実行URLを記載する。実行URLを取得できない場合は、対象CommitのChecks画面へのURLを記載する。起動を確認できない場合は、未起動と断定せず、確認時点で実行を確認できなかったこととChecks画面へのURLを示す。
   - CIが実行中・待機中でも、実装担当は完了まで待機したり、定期的な再確認を続けたりする必要はない。実装・Pushの報告とユーザーへの確認依頼を通常どおり行い、次の作業へ進んでよい。CIの未完了は未完了として明示する。
   - CIがFailureであることを確認した場合は、確認できる範囲で失敗したJob／テストを特定し、今回の変更との関連性を既知の基準結果等と照合する。今回の変更に関係する新たな失敗、変更前から存在する失敗、今回の変更と無関係な失敗、関連性を判断できない失敗を区別する。失敗の原因を確認できない場合は推定で断定せず、未確認として報告する。独立した範囲外の問題を無断で修正しない。
7. 作業報告では、実装・自動検証・ユーザー実機確認・CI・公開反映を分け、未実施・未確認・未完了を明示する。日常的な進行記録をGitHubへ追加しない。

## 4. 作業中断・再開

- 会話や処理が中断した場合、Commit・Push・検証が完了したと推測しない。現在の会話と実際に利用できる作業環境の状態を確認し、GitHub上の最新 `main` および該当するPR／Previewがある場合はその状態と照合する。
- 作業ツリーに未保存変更が残っている場合は、その変更を実際に保持している環境を確認し、その環境内で差分と保存状態を保全する。出所不明の変更を上書き・破棄せず、復旧のためだけに別環境へ自動移行しない。
- ローカル環境を利用した担当者は、作業中もローカルに残る変更と作業状態を把握・記録する。担当交代・中断時には、次の担当者が状態を確認して継続できるよう、少なくとも実際の作業環境・リポジトリパス・ブランチ・HEAD、変更済み／未追跡ファイルと保存状態、作業位置、実施済み／未実施の検証、未完了事項を現在の会話内で共有する。ローカルに未完了の変更がない場合も、その旨を明示する。
- 会話の状況伝達や担当交代だけを目的に、HANDOVER、作業ログ、relayブランチを作成しない。ローカル作業状態の記録・共有はこの例外的な責務を満たすためのものであり、GitHubへ進捗記録を新設することを意味しない。再開時は、ユーザーの最新指示・現在の会話・GitHubに実在する成果物と変更履歴、およびローカル利用時に共有された作業状態を基準にする。

## 5. 仕様書管理と継続的整合性確認

本節をOctober2026の文書管理手順の唯一の正本とし、相談役が作業時に適用する。実装内容の転記ではなく、将来も守る設計原則・制約・例外を管理する。

### 5.1 文書の種類・責務・正本

| 情報 | 正本と責務 |
| --- | --- |
| 現在の設問・教材・語彙・表示文言・選択肢 | ページの実装コード |
| 共通機能・動作・設計 | [PROJECT_SPEC.md](PROJECT_SPEC.md)：音声・録音・STT/TTS・状態保持・表記／教材の基本原則 |
| 共通表示・操作配置・レイアウト | [UI_LAYOUT_SPEC.md](UI_LAYOUT_SPEC.md)：PROJECT_SPECの機能要件を前提とする共通UI契約 |
| ページ／密接なページ群の重要な制約 | 承認済みの該当ページ固有仕様書。教育上の理由・重要な例外・複雑な固有設計・不変条件を扱う |
| 作業手順・同期・文書管理 | [AGENTS.md](../AGENTS.md)は入口・必須ガード、本書は詳細手順。教材仕様は参照し、複製しない |
| 現在の作業状況・未完了事項・次の一手 | 相談役が現在の会話内で管理する。GitHubに日常的な進行記録は作らない |
| 自動テストの具体的検証手順 | テストコード。仕様書には特別な検証条件・守る要件のみ置く |

同じ規則は一か所で管理し、別文書には実在するファイル・見出しへの参照を置く。UI_LAYOUT_SPECとPROJECT_SPECにまたがる事項も責務ごとに分け、同じ規則の正本を二つ作らない。承認済みの個別例外は範囲と理由を固有仕様へ記録し、共通仕様を重複記載しない。既存の重複記録は整理の承認まで残すが、新たな転記・同期義務の根拠にはしない。古い記録から適用範囲を自動的に広げない。

### 5.2 ページ固有仕様書の新設判断と承認

新しいPracticeページを作るだけでは仕様書を新設しない。次の条件がある場合だけ作成を検討する。

- A：共通UI・録音・状態保持・表示・判定などからの重要な例外。
- B：コードからは判断できない教育上の重要な制約。維持する文型の理由、意味・ニュアンスの区別、文法的に可能でも教材上認めない表現、学習段階の特別な制限など。
- C：選択と録音結果の特殊な対応、独自判定、複数行の特殊な保持など、共通部品では説明できない複雑な固有設計。
- D：設計理由を残さないと将来の担当者が誤って変える危険の高い判断。

該当しても直ちに独立文書を作らない。既存共通仕様で扱えるか → 既存のページ群仕様へ追記できるか → 短いコードコメントで足りるか → 独立文書が本当に必要か、の順で判断する。

独立文書が必要なら、編集前に「新設理由／記録する重要な制約／既存文書では管理できない理由／提案ファイル名」を報告し、ユーザーの承認後に作る。相談役・分析役・実装担当は独断で新設しない。ユーザーが明示的に新設を指示した場合は追加承認を求めない。

### 5.3 記録する内容・記録しない内容

記録するのは、学習目標・重要な文型制約、意味やニュアンスの教育上の判断、共通仕様からの例外と理由、特殊な状態遷移／判定、不変条件、特別な検証条件。

記録しないのは、Drill／Exampleの全設問、現在の動詞・目的語・語彙一覧、タイトル・説明文・Notice全文、選択肢・ラベルの全リスト、コードで直接分かる画面構成、実装を文章へ置換した説明、日々の変更履歴。特定の語や文言そのものが重要な制約なら、その理由と必要最小限の例だけを記録できる。現在の実装の記録と将来も維持すべき制約を区別する。

### 5.4 更新・統合・整理・廃止

設計原則、固有の重要制約、例外、特殊機能／状態遷移が変わった場合、または文書の誤り・矛盾を見つけた場合は、該当する正本を更新する。

設問の追加削除・順序変更、語彙差替え、タイトル／説明文／Noticeの表現変更、微小なレイアウト調整、既存仕様どおりに戻す通常の不具合修正は、原則として仕様書更新不要。ただし重要制約自体に影響すれば必要部分を更新する。コード変更と仕様書更新を機械的に連動させない。

同じ規則がページ固有仕様で繰り返される場合は共通仕様への統合を検討するが、似ているだけで動作が異なるものを無理に統合しない。適用範囲が変わる統合は事前承認を得る。

肥大化した文書は、コード重複 → 他文書重複 → 古い実装状態 → 解決済みの一時問題 → 同じ規則の繰返し、の順で整理し、重要制約を残す。固有制約がなくなれば廃止を提案する。既存仕様書の廃止・統合・大幅削除は、対象と残す情報を提示し、ユーザーの事前承認後に実施する。履歴・検証根拠の保全方法も示す。

### 5.5 通常変更時の整合性確認と報告

「仕様書が最新」とは、実装と記載された設計原則・制約・例外が矛盾せず、重要な未記録事項がないこと。設問・文言・語彙の全文一致ではない。

各変更の完了前に差分が共通仕様、ページ固有制約、例外、学習目標／文法判断、状態保持・判定・録音等の要件、既存文書の正確性へ影響するか確認する。関係する文書だけを読み、毎回全仕様書を読み直さない。影響なしなら更新不要、影響ありなら該当正本を更新する。有効な仕様に反する変更を文書の書換えで既成事実化せず、ユーザーに確認する。

完了報告へ差分に基づく **更新不要／更新済み／要確認** を添える。更新しただけで実装整合を確認できていない場合は確認済みと報告しない。要確認は矛盾・判断待ちの内容を記す。

### 5.6 作業完了時の対象範囲に応じた仕様整合性確認

実装担当がページ作業完了を宣言した後に最終確認を行う場合は、本書「2. 作業・保存・検証」の[ページ作業完了と作業範囲に応じた最終確認](#ページ作業完了と作業範囲に応じた最終確認2026-11-04確定2026-11-16整合整理)に従う。今回の変更箇所・直接影響を受ける範囲に関係する最新実装・共通仕様・対象ページ／ページ群仕様・重要制約・未解決事項を照合する。ページ作業完了の宣言だけで対象ページ全体や全仕様書の監査を自動開始しない。ユーザーが明示した全体監査・受入条件、または変更の影響範囲が広い場合に限り、その必要範囲へ拡張する。相談役・分析役は実装担当の宣言なしにページ作業完了を独自に宣言しない。別途明示的テスト指示には従う。

確認項目は、実装との矛盾、古い実装状態の現行扱い、廃止機能の残存、新たな重要制約／例外の未記録、規則の重複管理、参照先の実在・リンク切れ、文書が実装の複製へ戻っていないか。コードとの機械的全文一致は求めない。

矛盾は次で分類する。

| 分類 | 判断と対応 |
| --- | --- |
| A：文書が古い | 実装が承認済み変更を反映していることを確認し、古い記述を削除・更新。大幅整理は5.4の承認手順に従う |
| B：実装が有効な仕様に違反 | 重要制約は維持し、不一致を報告。実装に合わせて文書を書き換えない |
| C：正否・承認・意図が不明 | ユーザーに確認し、仕様・実装を独断で変更しない |

### 5.6.1 作業完了時の関連検証資産・一時実装の整理（全Practice共通／変更・影響範囲内／2026-11-16整合整理）

ページ作業完了宣言後の最終確認では、今回の作業範囲と直接影響を受ける範囲に関係する現行実装・承認済み教材／仕様・選択した関連自動テストを照合する。次の整理は該当範囲に関係する場合に行い、無関係なページ・機能・テスト資産へ監査を広げない。

- 選択した関連テストに旧教材・旧キュー・廃止済み設問等を前提とする期待値がある場合は特定する。現行仕様でも必要な回帰テストは期待値を更新して維持し、現行仕様で検証対象が存在しないテストだけを削除する。失敗を隠すために期待値を無条件で削除・緩和しない。
- 対象ページの今回の作業範囲・直接影響範囲に残る暫定表示・試験機能・デバッグ情報・一時検証コード・不要な生成物や参照・廃止機能の残存を確認し、現行の機能・教材・テストに不要と確認できたものだけを整理する。無関係な箇所や不要と確認できないものは独断で削除しない。
- 関連仕様書のうち今回の作業に関係する範囲に古い実装状態・解決済みの一時事項があれば、5.4に従い整理し、必要な設計制約・検証根拠・有効な回帰防止策を保持する。文書の廃止・統合・大幅削除は既存の事前承認手順を守る。
- 実際に整理した変更の影響範囲に必要なテストだけを再実行し、削除・更新した対象、理由、結果、判断待ち・未確認の項目を最終報告する。共有コード・他ページ・歴史的証跡へ影響する削除や意図が不明な資産はユーザーに確認し、対象ページ外の無断整理を行わない。

この確認・整理の考え方は全Practiceページに共通するが、実施範囲は今回の作業・直接影響を受ける範囲に限る。ページ作業完了の宣言だけを理由に、無関係なページ・機能・テストを含む全体整理・包括テストを開始しない。

### 5.7 最終確認・ページ全体テストを実施した場合の変更確定

不具合修正後は仕様書への影響を再判定し、必要な更新と影響範囲の再検証を終えて最終整合性を確認する。ページ全体テストを実施した場合も、判定はそのテストの対象範囲に限る。未解決の仕様矛盾が残る範囲は検証完了としない。一方、有効仕様との矛盾がなく将来の文書改善案だけが残る場合は、依頼された成果の完了を妨げない。

必要な仕様書更新は関連コードと整合する同じ作業単位でGitHubへ確定する。未確定設計を承認済み仕様へ混ぜず、未解決としてユーザーへ報告する。作業状況の保存だけを目的とするCommitやPushは行わない。

毎回全ページを再監査する必要はない。変更内容に応じた影響範囲を検証し、対象・検証条件・結果・未確認事項を作業報告に示す。

### 5.8 共通仕様の新設・変更時の適合監査と是正完了義務（2026-11-07確定）

共通仕様の新設・変更・適用範囲拡大は、文書登録だけで既存実装への適用を完了したことにならない。仕様の確定と適用・検証を以下の独立した工程として扱い、全Practice共通規則は原則として全対象ページに適用する。特定のページ群のCSSを共有している事実は、共通仕様の対象をそのページ群に限定する理由にならない。

1. **影響範囲の棚卸し**：共通仕様を新設・変更した担当者は、対象となる全ページ・Example／Drill・共通部品・ページ固有の上書き・既存テストを列挙する。既存実装の適合状況を調べ、未確認を適合済みと扱わない。ページ固有の承認済み例外は、理由と範囲を照合する。
2. **状態の分離**：少なくとも「仕様登録済み」「影響調査済み」「実装対応済み」「再検証済み」「ユーザー実機確認済み」を別々に記録する。文書更新やPush、デプロイ成功のみで後続工程を完了扱いしない。未対応・未検証箇所と検証条件を作業報告で明示する。GitHubに日常的な進行状況の記録を作らない。
